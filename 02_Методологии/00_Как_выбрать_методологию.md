# Как выбрать методологию

**Статус:** основной.

Методология вводится для управления конкретным риском. Чем меньше риск и scope,
тем меньше нужно артефактов.

| Вопрос | Подход |
|---|---|
| Меняется наблюдаемое поведение? | SDD и review требований человеком |
| Восстанавливается уже утверждённое поведение? | Тест воспроизведения и исправление дефекта |
| Есть сложное детерминированное правило? | TDD для вычислительного ядра |
| Нужны общие бизнесу и разработке примеры? | BDD или ATDD |
| Есть конфликт терминов и сложная предметная модель? | Элементы DDD |
| Принимается долговечное техническое решение? | ADR |
| Оценивается недетерминированный ответ модели? | Eval |
| Повторяется техническая механика? | Шаблонизатор или runtime |
| Нужно найти зависимости и область влияния? | Граф как индекс |

## Методы могут сочетаться

SDD фиксирует требуемый результат. BDD раскрывает его примерами. TDD помогает
реализовать отдельные правила. ADR сохраняет технический выбор. CI запускает
проверки, а граф помогает найти связанные артефакты.

Совместное применение не превращает методы в обязательные стадии. Простая
правка может использовать один тест. Изменение платёжного контракта может
потребовать SDD, ADR, contract tests и реальную интеграционную проверку.

## Признаки избыточной методологии

- документ повторяет уже известное, не уменьшая риск;
- артефакт создаётся только ради заполнения шаблона;
- одно утверждение копируется в несколько канонов;
- проверка доказывает механику инструмента, а не проектное отличие;
- стоимость синхронизации выше стоимости возможной ошибки.
