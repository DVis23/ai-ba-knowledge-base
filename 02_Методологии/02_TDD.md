# Test-driven development

**Статус:** основной.

TDD превращает детерминированное правило в короткий цикл обратной связи. Перед
реализацией разработчик создаёт исполнимый пример и видит, что он падает по
ожидаемой причине. Затем добавляет минимальный код и улучшает структуру, не
меняя уже проверенный результат.

```text
Red: ожидаемое поведение ещё отсутствует
  ↓
Green: минимальная реализация даёт нужный результат
  ↓
Refactor: устройство улучшается при зелёном тесте
  └───────────────────────────────→ следующий пример
```

Цикл работает, только если известен тестовый оракул — способ отличить
правильный результат от неправильного. Для округления это ожидаемое число, для
перехода состояния — допустимая следующая стадия. Оракул должен происходить из
утверждённого правила, а не из текущего кода, иначе тест закрепит существующую
ошибку.

TDD особенно полезен для формул, границ, классификаторов, merge, deduplication,
permissions и воспроизводимых дефектов. Набор примеров растёт от обычного случая
к границам и значимым взаимодействиям. После исправления дефекта его пример
остаётся регрессией.

Метод не требует тестировать каждую строку или повторять стандартную механику
платформы. Проверяется проектное правило и место, где ошибка действительно
может возникнуть. TDD помогает построить реализацию, но не решает, какое
поведение продукт должен утвердить; при изменении контракта ему предшествует
SDD или другое человеческое решение.
