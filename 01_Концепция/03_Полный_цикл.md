# Полный цикл

Сквозная цепочка от слов заказчика до работающего кода. Карта: что за чем идёт, что производит каждая стадия, чем удержан ИИ. Как делать каждую стадию — в [02_Процесс](../02_Процесс/).

## Цепочка целиком

```mermaid
flowchart TD
    M[Встреча с заказчиком] -->|транскрипт| R[Рафинат встречи<br/>D / R / PAIN / Q]
    R --> BA[БА-документация<br/>ST → BR → BP → правила → функции]
    BA --> S[Спеки OpenSpec<br/>Requirement / Scenario / AC]
    S --> C[ИИ-кодинг<br/>код + тесты, @trace]
    C -->|прототип, диктовка, багрепорт| S
    BA --> G[(Граф проекта)]
    S -.-> G
    C -.->|@trace, тест-доказательства| G
    G -.->|lint / impact / coverage / gate| BA
```

Поток вниз — создание знания. Поток вверх — наблюдение реальности: прототипы, диктовки, багрепорты возвращаются в канон. Пунктир — граф: сквозной индекс, который держит оба потока проверками.

## Стадии

|Стадия|Производит|Семья фреймворка|Инструмент|Как делать|
|---|---|---|---|---|
|**1. Встреча → требования**|рафинат встречи с маркерами `[D]/[R]/[PAIN]/[Q]`|документная|skill `ba-refine-meeting`|[01_Требования_и_встречи](../02_Процесс/01_Требования_и_встречи.md)|
|**2. БА-документация**|артефакты бизнес-знания: `ST`, `BR`, `BP`, `BR-XX`, `BD`, `DM`, `BF`|документная|skills `ba-generate-*` + граф-инструмент|[02_БА_документация](../02_Процесс/02_БА_документация.md)|
|**3. Спеки**|capability: `Requirement`/`Scenario` (AC), контракт `design.md`|документная|OpenSpec ([арх-фреймворк](../03_Фреймворки/05_Архитектурный_фреймворк.md) — справочно)|[03_Спеки_и_архитектура](../02_Процесс/03_Спеки_и_архитектура.md)|
|**4. ИИ-кодинг**|работающий код + тесты, трассированные к AC|кодовая (рантайм)|код-фреймворк|[04_ИИ_кодинг](../02_Процесс/04_ИИ_кодинг.md)|

## Проект — один репозиторий

Зрелая форма цикла — **монорепозиторий продукта**, где живут все слои сразу:

|Слой|Что лежит|
|---|---|
|Входы|рафинаты встреч, диктовки, исследования интеграций|
|БА-корпус|`ST`/`BR`/`BP`/`BD`/`BF`, глоссарий, реестр открытых вопросов|
|Спеки|`specs/` (текущая истина) + `changes/` (изменения)|
|Код|backend, админка, мобильные приложения, тесты|
|Автоматизация|граф-инструмент, валидаторы, гейты, Makefile, CI|
|Контракт агента|`AGENTS.md`/`CLAUDE.md`, skills, hooks|

Почему это принципиально:

- **Граф сквозной.** Ребро «правило → спека → код → тест» существует физически только когда всё в одном репозитории.
- **Агент видит всё.** Контекст любой стадии достижим без «сходи в другую систему».
- **Изменение знания = ветка + MR.** Документация проходит тот же контур ревью и слияния, что код: ветки `docs/*` рядом с `feat/*`.
- **Одна автоматизация.** Линтер доков, валидатор спек и тесты кода — в одном CI.

## Цикл — не водопад: обратные потоки

Схема сверху вниз описывает **поток истины, не хронологию**. В бою код часто существует раньше канона:

- **Прототип-first.** По БА-корпусу генерируется прототип интерфейса; дизайн правится прямо в нём. Прототип — черновик поведения, не источник.
- **Диктовка поверх живого экрана.** Аналитик проговаривает поведение по работающему прототипу — получаются сырые критерии приёмки (RAC-слой).
- **Сведение слоёв.** Канонический AC рождается сведением трёх источников: БА-корпус + прототип + диктовка. Конфликты решает владелец продукта явно, а не модель молча.
- **Эксплуатация возвращает знание.** Багрепорт или демо → канон-правка спеки → код. Не наоборот.

Инвариант при любом порядке: **источник истины — канон** (решения, правила, спеки). Код и прототип — наблюдения; их расхождение с каноном помечается (`TRACE-GAP`), а закрывается правкой канона, не молчаливым принятием кода.

## Слои доверия источников

У каждого файла проекта есть класс происхождения — от первоисточника к производному:

```
человеческий первоисточник (транскрипт, диктовка)
  → рафинированный человеческий вход (рафинат — вычищен, но смысл человеческий)
  → производная модель (БА-артефакты, индексы, reconciliation-отчёты)
  → канон (принятые спеки и правила)
  → доказательства реализации (код, тесты)
```

Реестр происхождения ведётся отдельным документом и отвечает на вопрос модели «чем можно обосновать факт»: число из канона бьёт число из производного индекса; диктовка остаётся первоисточником, даже если её текст вычистил агент. Машинная форма этой лестницы — origin-словарь [графа](../03_Фреймворки/02_Граф.md).

## Открытые вопросы — сквозной механизм

Незнание фиксируется, а не сглаживается, на каждой стадии одним механизмом: маркер `[Q]` в рафинате → реестр открытых вопросов (категории, статусы, владельцы) → `Q-N`/`OQ-N` в артефактах и спеках → закрытие с датой, автором и решением. Догадка без открытого вопроса — запрещённый ход (assume → mark).

## Порядок внутри БА и спек

Жёсткий конвейер только внутри БА (каждый шаг потребляет предыдущий):

```
рафинат → стейкхолдеры (ST) → требования (BR.X) → процессы (BP)
        → правила (BR-XX) → функции (BF, индекс)
```

Параллельно по ходу: решения `BD`, доменная модель `DM/EN/SM`, модули `M`. **Спеки — после БА** в смысле истины: они цитируют решения и правила, а не код или догадку. Хронологически код-прототип может появиться раньше канона (см. обратные потоки) — источником он от этого не становится.

## Трассировка насквозь

Один факт проходит всю цепь и нигде не дублируется:

```
встреча: «скидка лояльности — 15%»
  → BD-02 (решение, кто и когда принял)
  → BR-10 (правило: формула и условия)
  → спека: Requirement + Scenario (AC-CART-014), Trace: BD-02 §2, BR-10
  → код: // @trace: AC-CART-014, BR-10
  → тест: сценарий по AC-CART-014 — тест-доказательство в графе
```

Поменялось решение — `impact BD-02` показывает всю цепочку вниз: какие правила, спеки, код и тесты протухли. Обратно: `gate` изменения не пустит в релиз AC без тест-доказательства. Это и есть смысл связки фреймворк + граф на полном цикле.

## Кто это ведёт

Всю цепь ведёт один [фулл-стек ИИ-специалист](01_Зачем_ИИ_в_ИТ_проекте.md): на каждой стадии он берёт нужный фреймворк, держит ИИ в рамках и проверяет результат. Документные фреймворки (стадии 1–3) переиспользует, код-фреймворк (стадия 4) при необходимости [строит сам](../03_Фреймворки/06_Код_фреймворк.md).
