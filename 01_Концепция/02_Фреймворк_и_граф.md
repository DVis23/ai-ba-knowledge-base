# Что такое фреймворк и граф

Точные определения понятий, на которых стоит база. Без них термины расползаются: «фреймворком» называют то метод, то схему артефактов, то инструмент — и появляется каша.

## Лестница терминов

|Термин|Что это|Пример|
|---|---|---|
|**Приём**|инвариант метода: зафиксируй форму → освободи содержание → проверь автоматически|один на все стадии|
|**Фреймворк**|приём, упакованный для стадии: **схема** + **процедуры** + **проверки**|БА-фреймворк, спеки (OpenSpec), код-фреймворк|
|**Схема**|контрактная часть фреймворка: типы артефактов, ID, обязательные секции — или типы деклараций в коде|таксономия `ST`/`BR`/`BP`; дескриптор `Resource`|
|**Skill**|процедура наполнения схемы, исполняемая ИИ|`ba-generate-rules`|
|**Граф**|сеть артефактов проекта: узлы + типизированные рёбра. Данные, не программа|граф конкретного проекта|
|**Граф-инструмент**|домен-агностичный движок: строит граф из файлов по конфигу, отвечает на запросы, проверяет целостность|CLI: `import` / `impact` / `lint` / `gate`|
|**Среда**|где исполняются процедуры и живут агенты|Claude Code|

Сборка: фреймворк = схема + skills + проверки. Граф-инструмент и валидаторы **обслуживают** фреймворки, среда **исполняет** процедуры. Слово «фреймворк» в базе всегда означает упаковку целиком, не схему и не инструмент.

## Граф — это фреймворк?

Нет — и это главный источник путаницы. Фреймворк **задаёт форму** домена. Граф-инструмент формы не знает: он **потребляет** её из конфига (типы, ID-regex, ожидаемые связи), а сам только строит сеть, проверяет и отвечает на запросы. Отношение то же, что между схемой данных и СУБД: схем много — БА, спеки, — движок один.

|Убрать|Что останется|
|---|---|
|фреймворк|граф-инструменту нечего строить: нет типов и ID — нет узлов|
|граф|фреймворк слепнет: impact и проверки связности руками не делаются|

В [триаде](../03_Фреймворки/01_Триада.md) документной семьи это разные ноги: Схема + Skill + Граф. У кодовой семьи роль графа исполняют компилятор и drift-снимки; зрелый граф при этом пришивает и код — узлами реализации ([Граф](../03_Фреймворки/02_Граф.md)).

## Фреймворк для ИИ

**Фреймворк для ИИ = контракт между человеком, моделью и инструментами + автоматические проверки этого контракта.**

Контракт фиксирует **форму** результата (шаблон, схему, типы), оставляя модели только **содержание**. Проверки ловят нарушения формы машинно. Один приём решает все три слабости LLM сразу:

|Слабость LLM|Чем закрывает фреймворк|
|---|---|
|Стохастичность|форма зафиксирована — «плавает» только содержание в заданных рамках|
|Ограниченный контекст|модели подаётся нужный кусок (срез графа / одна декларация), не весь проект|
|Невалидируемость|форма проверяема скриптом: линтер / компилятор / тесты|

Без контракта три стороны не сходятся: человек хочет одно, модель выдаёт другое, тулинг не понимает ни того, ни другого.

## Инвариант: один приём на всех стадиях

Фреймворк нужен на каждой стадии проекта. Меняется материал — приём один: **зафиксируй форму, освободи содержание, проверь автоматически.**

|Стадия|Форма (что фиксируем)|Содержание (что отдаём ИИ)|Проверка|
|---|---|---|---|
|БА / спеки|схема артефакта: секции, ID, ссылки|бизнес-смысл, поведение|линтер + граф|
|Код|декларации + кодогенерация + слои|сложная бизнес-логика|компилятор + drift + линтер + тесты|

Кто усвоил приём — поднимет любую стадию. В этом суть фулл-стек ИИ-специалиста.

## Две семьи фреймворков

Различаются тем, **во что упакован контракт**:

|Семья|Контракт лежит в|ИИ генерирует|Проверки|
|---|---|---|---|
|**Документная**|markdown-артефактах с типами и ID|артефакты (требования, спеки)|линтер + граф|
|**Кодовая (рантайм)**|типизированных декларациях + кодогенерации|только бизнес-логику; обвязку генерит фреймворк|компилятор + drift-снимки + арх-линтер + тесты|

Документная — для БА и спек (markdown переиспользуем как есть). Кодовая — для самой разработки и привязана к стеку (готовую редко берёшь — [строишь сам](../03_Фреймворки/06_Код_фреймворк.md)).

## Граф

**Граф = проект, представленный как сеть: артефакты — узлы, связи по ID — типизированные рёбра.** Не метафора, а структура данных с запросами.

Куча markdown-файлов и граф из тех же файлов отличаются тем, что можно спросить:

|Вопрос|Без графа|С графом|
|---|---|---|
|Что сломается, если поменять это правило?|ручной grep + надежда|запрос `impact <ID>`|
|Все ли требования покрыты спеками, все ли AC — тестами?|глазами по 300 файлам|запросы `coverage`, `gate`|
|Нет ли висячих ссылок, циклов, сирот?|не выявить вручную|запрос `audit`|
|Какой контекст дать модели по этому узлу?|весь репозиторий|срез: узел + типизированные соседи|

Зрелый граф — **сквозной**: узлами входят не только документы, но и код, тесты, элементы UI — трассировка «решение → правило → спека → код → тест» становится запросом. Граф нужен, когда документов много (сотни артефактов, тысячи связей); на десятке файлов хватит папки. Устройство → [Граф](../03_Фреймворки/02_Граф.md).

## Сквозные принципы (документная семья)

Что делает фреймворк рабочим, а не стопкой шаблонов:

|Принцип|Что ломается без него|
|---|---|
|**Стабильные ID** (артефакт адресуется кодом, не названием)|трассировка распадается после первого переименования|
|**Single source of truth** (факт живёт в одном месте)|модель находит две версии и выбирает случайную|
|**Двусторонняя трассируемость** (артефакт знает предков и потомков)|невозможен impact-анализ|
|**Атомарность** (единица — то, что ИИ закрывает за один проход)|модель берётся за «всю фичу» и теряется|
|**Валидируемость = линтер** (для каждого правила — автопроверка)|правила живут только в голове автора|
|**Decision capture** (почему так — отдельный артефакт)|через месяц перерешают заново|
|**Assume → mark** (догадка ИИ помечена явно)|догадки выглядят как факты и попадают в код|
|**Провенанс** (у знания есть класс происхождения)|производный индекс побеждает первоисточник|

## Один способ запомнить

Приём один: **форма + содержание + автопроверка**. Фреймворк — упаковка приёма для стадии. Граф — не фреймворк, а сеть проекта; граф-инструмент — движок над ней, общий для всех документных фреймворков. Есть фреймворк и граф — ИИ надёжный исполнитель. Нет — генератор случайного текста, который нельзя ни проверить, ни связать.
