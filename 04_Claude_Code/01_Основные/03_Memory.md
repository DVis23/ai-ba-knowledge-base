# Memory

Персистентное файловое хранилище: факты, переживающие сессию. Не путать с контекстом окна — окно сбрасывается, memory нет.

## Зачем существует

1. **Долговременная индивидуализация.** CLAUDE.md одинаков для всех, кто работает в проекте. Memory — про конкретного пользователя и его контекст.
2. **Контекст не бесплатен.** Если положить все факты в CLAUDE.md — окно заполнится шумом. Memory подгружается по релевантности.
3. **Накопление feedback.** Каждая правка пользователя — потенциальное правило. Без memory одну и ту же ошибку придётся объяснять снова.

## Четыре типа

|Тип|Что хранит|Когда писать|
|---|---|---|
|**user**|Роль, цели, экспертиза пользователя|Узнал что-то о пользователе, что должно повлиять на будущее общение|
|**feedback**|Правила «как работать»: корректировки и подтверждения|Пользователь поправил подход ИЛИ принял нетривиальное решение без возражений|
|**project**|Текущие инициативы, дедлайны, кто что делает|Узнал контекст работы, не выводимый из кода/git|
|**reference**|Указатели во внешние системы (Linear, Grafana, Slack)|Узнал, где лежит источник правды вне репозитория|

## Что НЕ писать (даже если просят)

- **Код, конвенции, архитектуру** — выводится из чтения кода.
- **Git history** — есть `git log` / `git blame`.
- **Решения багов** — фикс уже в коде, причина в коммите.
- **Эфемерное**: in-progress работа, текущий разговор — для этого план и таски.
- **Длинные сводки/списки**: если просят «запомни PR-ы за неделю», спроси что в них *неочевидного* — сохрани только это.

Исключения применяются, даже если пользователь явно просит сохранить.

## Формат файла

```
---
name: kebab-case-slug
description: одна строка — по ней решается релевантность в будущем
metadata:
  type: user | feedback | project | reference
---

Содержимое.

Для feedback/project структура:
- Правило/факт
- **Why:** причина (часто прошлый инцидент или предпочтение)
- **How to apply:** когда и где применяется
```

Связи: `[[other-name]]` — линкуй щедро, даже если файла-получателя ещё нет. Это маркер «надо написать», не ошибка.

## MEMORY.md как индекс

Один файл `MEMORY.md` — индекс, не хранилище. Каждая строка ≤ 150 символов: `- [Title](file.md) — one-line hook`. Грузится в каждую сессию целиком — после 200 строк начинает обрезаться.

## Когда читать

- Тема разговора пересекается с записанным — релевантность очевидна.
- Пользователь явно просит вспомнить.
- **Перед действием на основании memory**: верифицируй, что факт ещё актуален. Memory ≠ текущее состояние; названный файл/функция/флаг могли быть переименованы или удалены.

## Что делать со stale

- Файл больше не существует → удалить memory.
- Факт устарел → обновить.
- Никогда не «дописывай» противоречие: чистая правка, чтобы не было двух версий одного факта.

## Принципы дизайна

|Принцип|Что значит|Что ломается без него|
|---|---|---|
|**Одна запись — один факт**|Не валить роль, дедлайн и систему трекинга в один файл|Невозможно обновить часть без перезаписи всего|
|**Описание = критерий поиска**|`description:` решает, найдётся ли запись в будущем|Запись есть, но никогда не подтянется|
|**Why + How to apply**|Не голое правило, а с причиной и сценарием|Через месяц неясно, применять ли в новом случае|
|**Глаголы в активном залоге**|«Пользователь предпочитает X», не «X было упомянуто»|Стиль summary, не правила — теряется императивность|
