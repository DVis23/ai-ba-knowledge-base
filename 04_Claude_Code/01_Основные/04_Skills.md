# Skills

Skill = **триггерируемая процедура с контекстом**, упакованная в один файл. Не промпт, не агент, не memory, не CLAUDE.md — сравнение всех четырёх механизмов в [01_Обзор.md](../01_Обзор.md).

Если поведение должно срабатывать **на конкретное условие и выполнять процедуру** — это skill. Всё остальное — другой механизм.

## Зачем skill-ы существуют

1. **Контекст не бесплатен.** Если положить инструкции в CLAUDE.md — они всегда в окне, даже когда не нужны. Skill грузится только когда триггер сработал.
2. **Процедурное знание ≠ декларативное.** «Платёж проходит за 3 секунды» — факт, идёт в memory/docs. «Как создать артефакт по шаблону: собрать зависимости, прочитать предков, сгенерить целевую структуру, проверить» — процедура, идёт в skill.
3. **Повторяемость без копипасты.** Если объясняешь Claude одно и то же третий раз — это skill. Один раз формализуешь, дальше вызываешь `/<name>`.
4. **Переносимость.** Skill уезжает в другой проект вместе с файлом. Memory — нет. Промпт в чате — тем более нет.
5. **Композиция.** Skill вызывает агентов, другие skill-ы, tools. Это единица оркестрации, а не текстовый сниппет.

## Как разрабатываются

1. **Источник — повтор.** «В третий раз объясняю Claude как обработать этот тип входа». В этот момент skill уже должен был существовать.
2. **Анатомия skill-а:**
    - **Trigger** — однозначное условие срабатывания («когда пользователь даёт транскрипцию встречи»). Без него skill либо не вызывается, либо вызывается невпопад.
    - **Inputs** — что должно быть на входе (файл, ID, флаг). Если входы неявные — skill хрупкий.
    - **Steps** — последовательность с понятной декомпозицией. Не «сделай хорошо», а «1. собери X, 2. прочитай Y, 3. сгенерь Z».
    - **Outputs** — какой артефакт/состояние на выходе. Должно быть проверяемо.
    - **Validation** — финальный шаг, который проверяет результат (линтер, schema-check, тест).
3. **Тест на боевом кейсе.** Skill, который не прогнали на 2-3 реальных входах — сырой. Триггер ловит не то, шаги ломаются на edge case.
4. **Итерация через корректировки.** Каждое «нет, не так» — это либо правка skill-а, либо memory-feedback. Если правка повторяется — skill.
5. **Документ skill = его контракт.** Описание во frontmatter — то, по чему LLM решает, вызывать его или нет. Размытое описание = skill не находится.

## Принципы дизайна

|Принцип|Что значит|Что ломается без него|
|---|---|---|
|**Точный триггер**|Условие срабатывания однозначно, без «возможно, если»|Skill либо не вызывается, либо вызывается всегда|
|**Одна ответственность**|Один skill — одна процедура. `/generate-rules` не делает требования|Skill превращается в god-object, ломается на каждом изменении|
|**Явные входы/выходы**|Skill знает что получает и что отдаёт|LLM додумывает входы, выход непроверяем|
|**Self-contained**|Skill подгружает нужный контекст сам (читает файлы, делает grep), не полагается на «должно быть в окне»|Работает только в идеальной сессии, ломается на холодном старте|
|**Идемпотентность**|Повторный запуск с тем же входом даёт тот же результат, не дублирует|Skill одноразовый, конвейер собрать нельзя|
|**Dual mode**|Работает и на создание, и на инкрементальное обновление|После первого прогона skill заморожен|
|**Валидация в конце**|Последний шаг — автопроверка (lint, schema check, тест)|Skill «успешно отработал», а результат битый|
|**Композиция**|Skill вызывает агентов и другие skill-ы, не дублирует их логику|Параллельная эволюция, расхождение поведения|
|**Discoverability**|Имя + описание триггера читаются — и LLM, и человеком|Skill есть, но никто (включая Claude) не помнит, что он есть|
|**Failure path**|Что делать если вход неполный — спросить, упасть, использовать default|Skill молча генерит мусор на плохом входе|
|**Стабильное имя**|`/refine-meeting` не переименовывается каждый месяц|Ломается каждая ссылка на skill в других skill-ах и memory|
|**Локальная конвенция**|Skill живёт по правилам проекта (ID, трассировка, конвенции из `_shared/conventions.md`)|Skill генерит «правильно по учебнику», но мимо проекта|

## Где провести границу

- Делал это однажды → промпт.
- Делал дважды, может пригодится → memory-feedback.
- Делал трижды или это процедура с шагами → **skill**.
- Skill стал больше 200 строк или ветвится на 5+ сценариев → **разбить на несколько skill-ов или вытащить агента**.
- Нужен длинный поиск/исследование внутри шага → **скилл вызывает Explore/Plan агента, не делает сам**.

## Связь с фреймворком

Skill без фреймворка работает, но не масштабируется. Skill вроде `/generate-requirements` опирается на фиксированный шаблон артефакта и фиксированную таксономию ID. Уберите шаблон — skill начнёт изобретать структуру каждый раз. Уберите ID — skill сгенерит, но граф не свяжет.

Подробнее, как это складывается с фреймворком и валидацией — [03_Фреймворки/01_Триада.md](../../03_Фреймворки/01_Триада.md).
