# Архитектурный пакет разработки

**Статус:** концептуальная альтернатива.

Этот подход нужен, когда требования уже описывают результат, но агенту всё ещё
приходится угадывать границы модулей, состояния интерфейса и место новой логики.
Архитектурный пакет последовательно сужает пространство решения: от системы
целиком до небольшого вертикального среза реализации.

```text
Architecture Overview
        ↓ границы системы
Module Boundaries + ADR
        ↓ допустимое устройство
Feature Spec + Screen State Machine
        ↓ поведение функции
Behavior Slices
        ↓ исполнимые вертикальные части
код и проверки
```

## От системы к функции

Architecture Overview сначала показывает продукт, внешних участников,
интеграции и ключевые ограничения. Он не перечисляет классы; его задача —
остановить случайное расширение границы системы.

Затем Module Boundaries задаёт разрешённые направления зависимостей и владельцев
данных. Например, domain не зависит от HTTP-клиента, а UI обращается к данным
через presentation. Если выбор нетривиален, ADR сохраняет контекст, альтернативы,
решение и последствия. Благодаря этому следующий агент видит не только правило,
но и причину его появления.

Внутри этих рамок Feature Spec описывает цель и сквозные пользовательские
исходы. Она не должна дублировать living spec другой SDD-системы. Если
продуктовый контракт уже существует, архитектурный пакет использует его как
вход и добавляет только недостающее представление реализации.

## От функции к состояниям экрана

Сложный экран редко сводится к happy path. Screen State Machine связывает
режимы интерфейса с событиями и эффектами:

| Текущее состояние | Событие | Следующее состояние | Эффект |
|---|---|---|---|
| `content` | пользователь обновил | `loading` | запросить свежие данные |
| `loading` | пришёл пустой список | `empty` | нет |
| `loading` | произошла ошибка | `error` | сохранить причину |

Состояние выделяется только тогда, когда меняет видимый результат или доступные
действия. Событие приходит от пользователя, системы или внешней среды. Эффект
покидает чистую модель состояния: вызывает API, сохраняет данные или выполняет
навигацию. Такое разделение не позволяет спрятать сетевой вызов внутри
непроверяемого UI-перехода.

Простой экран не требует формальной машины состояний. Документ оправдан, если
ошибки возникают именно из-за комбинаций loading, stale, offline, selection и
повторных действий.

## От состояний к Behavior Slice

Behavior Slice выбирает минимальный путь через все нужные слои с наблюдаемым
результатом. Вместо независимых задач «создать repository» и «добавить кнопку»
он формулирует: «пользователь обновляет список и видит свежие данные либо
понятную ошибку».

Срез связывает предусловия, trigger, ожидаемый результат, покрываемые состояния
и acceptance scenarios. Implementation hints могут подсказать пути файлов,
имена интерфейсов и расположение тестов. Они уменьшают архитектурный выбор
агента, но не становятся требованиями: структура кода может измениться при том
же поведении.

Автоматический валидатор проверяет ID, обязательные поля и ссылки между
артефактами. Архитектурный линтер сопоставляет часть module boundaries с кодом.
Эти проверки подтверждают форму и соблюдение границ, но не правильность
продуктового решения.

## Когда брать части, а не весь пакет

Если основная SDD-система уже хранит поведение, второй Feature Spec создаст
конкурирующий канон. В таком проекте из архитектурного пакета заимствуют только
недостающее: ADR для решения, State Machine для сложного UI или implementation
hints для агента. Полный набор оправдан лишь тогда, когда эти представления
регулярно уменьшают ошибки сильнее, чем увеличивают стоимость синхронизации.
