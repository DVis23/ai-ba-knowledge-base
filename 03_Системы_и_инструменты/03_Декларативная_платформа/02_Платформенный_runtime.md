# Платформенный runtime

**Статус:** концептуальный.

Шаблонизатор устраняет повторение в файлах, но не устраняет повторение во время
работы приложения. Каждый endpoint всё ещё может отдельно проверять права,
вести аудит, обрабатывать повтор запроса и обновлять кэш. Runtime переносит эту
механику в общий исполняемый путь.

## Путь одного запроса

Рассмотрим изменение заказа:

```text
HTTP-запрос
   ↓ идентификация операции и пользователя
декларация ресурса
   ↓ permission и область доступных строк
валидация входа
   ↓ стандартная CRUDL-операция или проектный service
транзакция
   ↓ audit, событие и инвалидация кэша
HTTP-ответ
```

Runtime получает запрос и находит декларацию ресурса. Ресурс здесь означает
тип управляемых данных: заказ, клиент или тариф. Из декларации runtime узнаёт
поля, связи, разрешённые операции и политики. Для обычного создания, чтения,
изменения, удаления и списка — набора CRUDL — этого достаточно, чтобы выполнить
операцию без отдельного обработчика для каждого ресурса.

Политики включаются в тот же путь, потому что должны действовать одинаково при
любом способе вызова. Permission отвечает, может ли пользователь выполнить
операцию; row scope сужает записи, к которым она применима. Idempotency не даёт
повтору одной команды создать второй эффект. Audit записывает уже совершённое
действие, а инвалидация удаляет устаревший результат из кэша.

Связь этих механизмов важнее их отдельных определений. Runtime не должен
сначала изменить заказ, а потом обнаружить отсутствие permission. Идемпотентный
ответ обязан соответствовать исходной авторизации, а событие и audit появляются
только после успешной транзакции.

## Когда CRUDL перестаёт быть достаточным

Операция `confirm_order` не является произвольным обновлением поля `status`.
Она проверяет допустимый переход, остатки и права, а затем согласованно меняет
несколько данных. Такое правило принадлежит проектному service.

Runtime остаётся вокруг сервиса: проверяет транспортный контракт, открывает
нужную транзакцию, вызывает проектный код и применяет общие последствия. Сам
service владеет только уникальным инвариантом. Так платформа не поглощает
продуктовый смысл, но проект не переписывает инфраструктурную механику.

Из этого следует лестница реализации:

1. обычные данные проходят через CRUDL;
2. суммы и группировки — через общий агрегат;
3. уникальное бизнес-действие — через именованную операцию и service;
4. нестандартный транспорт получает сырой адаптер, но передаёт правило сервису.

## Работа вне запроса

Если пользователь не должен ждать завершения, runtime передаёт работу общей
системе задач. Очередь сохраняет задачу, lease закрепляет её за одним
исполнителем, а политика повторов обрабатывает временную ошибку. Идемпотентность
становится обязательной: после сбоя исполнитель может не знать, успел ли
предыдущий вызов создать внешний эффект.

Для многошаговой интеграции одного retry недостаточно. Durable workflow хранит
пройденные шаги и ожидаемые внешние события. Он продолжает работу с последней
подтверждённой точки, а при необратимом сбое запускает предусмотренную
компенсацию. Простой синхронный вызов провайдера не нужно превращать в workflow,
если вызывающая сторона ждёт ответ и повтор не требует сохранённого состояния.

## Цена общей точки исполнения

Runtime управляет последовательностью и поэтому становится критической частью
приложения. Ошибка в нём затрагивает все ресурсы, обновление требует контракта
совместимости, а скрытая магия усложняет диагностику.

Хороший runtime делает путь запроса наблюдаемым и оставляет явный выход в
проектный код. Если общая политика используется только одной функцией или
требует множества исключений, ей не место в платформенном ядре.
