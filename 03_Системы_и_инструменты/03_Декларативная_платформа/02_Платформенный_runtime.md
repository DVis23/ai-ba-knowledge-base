# Платформенный runtime

**Статус:** концептуальный.

## Какую проблему решает runtime

Шаблонизатор убирает повторение в исходных файлах, но его работа заканчивается
до запуска приложения. Во время каждого реального запроса всё равно нужно
одинаково определить пользователя, проверить права, ограничить доступные
записи, открыть транзакцию, записать аудит и обновить кэш. Если каждый endpoint
реализует эту последовательность самостоятельно, правила начинают расходиться:
один маршрут забывает аудит, другой проверяет право после изменения данных, а
третий иначе обрабатывает повтор запроса.

Endpoint — это доступная клиенту точка API, принимающая конкретный вид запроса.
Runtime переносит общую механику всех таких точек в один исполняемый путь.
Runtime здесь означает часть платформы, которая работает внутри запущенного
приложения и применяет декларации и политики к настоящим запросам, задачам и
интеграциям. Политикой, или policy, называется настраиваемое общее правило —
например, требование авторизации, повторов или аудита, — одинаково применяемое
к нескольким операциям.

Его задача не в том, чтобы скрыть всю реализацию за магией. Он гарантирует
одинаковый порядок общих действий и оставляет явную границу, за которой
уникальное продуктовое правило выполняет проектный код.

## Как проходит один запрос

Рассмотрим изменение заказа:

```text
HTTP-запрос
   ↓ определение операции и пользователя
registry ресурса
   ↓ permission и область доступных строк
валидация входа
   ↓ стандартная CRUDL-операция или проектный service
транзакция
   ↓ audit, событие и инвалидация кэша
HTTP-ответ
```

HTTP-запрос сначала попадает в тонкий транспортный адаптер. Транспорт отвечает
за форму взаимодействия с клиентом: читает параметры, преобразует ошибки в
HTTP-ответы и передаёт вызов дальше. Он не должен содержать бизнес-правило,
потому что то же действие может позднее запускаться из фоновой задачи или
другого транспорта.

По имени операции runtime находит ресурс в registry. Registry — это собранный
при запуске каталог известных ресурсов, операций и политик. Ресурсом является
тип управляемых данных, например заказ, клиент или тариф. Его декларация
описывает поля, связи, разрешённые операции и общие правила обработки.

Для стандартных действий применяется CRUDL: создать запись, прочитать одну,
изменить, удалить или получить список. Поскольку форма этих действий
повторяется у разных ресурсов, runtime может выполнить их без отдельного
обработчика на каждый тип данных. Декларация сообщает, какие поля доступны для
чтения и записи, а общий механизм выполняет остальную последовательность.

## Почему политики находятся в одном пути

До чтения или изменения данных runtime применяет permission — правило,
определяющее, разрешено ли пользователю выполнять выбранную операцию. Одного
ответа «можно» недостаточно для списка или изменения записи, поэтому следом
применяется row scope: ограничение множества строк, доступных этому
пользователю. Например, оператор может читать заказы только своего ресторана.

Затем вход проверяется по типам и ограничениям декларации. Валидация не решает,
правильно ли действие с точки зрения бизнеса; она отсекает данные, которые не
соответствуют техническому контракту операции: отсутствующее обязательное
поле, неверный формат даты или неизвестное значение перечисления.

Само изменение выполняется внутри транзакции. Транзакция объединяет несколько
операций с базой в одно целое: либо они завершаются вместе, либо при ошибке ни
одна не считается совершённой. Только после успешного завершения можно
публиковать событие, сохранять audit и инвалидировать кэш. Audit — журнал того,
кто, когда и что изменил. Инвалидация удаляет устаревшее сохранённое значение,
чтобы следующий читатель получил актуальные данные.

Отдельно runtime обеспечивает idempotency — защиту от повторного эффекта одной
и той же команды. Клиент может повторить запрос после потери ответа, хотя
первый вызов уже создал заказ или списание. Идемпотентный путь узнаёт повтор по
ключу операции и возвращает согласованный результат вместо второго изменения.

Порядок этих механизмов является частью гарантии платформы. Runtime не должен
сначала изменить заказ, а затем обнаружить отсутствие permission. Повторный
ответ обязан соответствовать исходной авторизации и результату. Событие,
audit и очистка кэша должны относиться только к успешно зафиксированной
транзакции, иначе внешние потребители увидят действие, которого в базе нет.

## Где заканчивается стандартный CRUDL

Не каждое изменение записи является обычным update. Операция `confirm_order`
может проверять допустимость перехода статуса, наличие остатков и право
оператора, затем резервировать товары и согласованно менять несколько записей.
Такой набор условий образует бизнес-инвариант — правило, которое должно
оставаться истинным при любом способе вызова операции.

Инвариантом владеет проектный service: именованный модуль с уникальной
бизнес-операцией. Runtime остаётся вокруг него — проверяет транспортный
контракт, создаёт контекст пользователя и транзакцию, вызывает service и
применяет общие последствия. Service не переписывает аудит, идемпотентность и
кэш, а платформа не присваивает себе продуктовое решение о том, когда заказ
разрешено подтверждать.

Из этой границы следует последовательность выбора механизма:

1. Обычные чтение и запись одного ресурса выполняются через CRUDL.
2. Суммы, счётчики и группировки выполняются общим aggregate-механизмом,
   который рассчитывает результат на стороне хранилища без загрузки всех строк.
3. Уникальное бизнес-действие оформляется как именованная операция и service.
4. Необычный протокол получает собственный транспортный адаптер, но передаёт
   продуктовое правило тому же service.

Такой порядок не запрещает специальный код. Он требует сначала проверить,
действительно ли задача выходит за стандартный путь, а затем локализовать
исключение в понятной точке.

## Когда работа выходит за границы запроса

Не всякую операцию пользователь должен ждать в открытом HTTP-соединении.
Долгий импорт, массовая рассылка или повторяемый вызов внешней системы
передаются общей системе задач. Задача сохраняется в очереди — хранилище
ожидающей работы, из которого отдельные исполнители забирают элементы.

Чтобы два исполнителя не выполнили одну задачу одновременно, очередь выдаёт
lease: временное право одного работника обрабатывать конкретный элемент. Если
исполнитель перестал подтверждать lease, задача снова становится доступной.
Поэтому обработчик обязан быть идемпотентным: после сбоя система не всегда
знает, успел ли предыдущий запуск создать внешний эффект.

Временные ошибки обрабатывает retry policy — правило повторов с ограничением
числа попыток и паузами между ними. Повтор помогает при краткой недоступности,
но не исправляет неверные данные или запрещённую операцию. Такие постоянные
ошибки должны завершать задачу с понятной диагностикой, а не создавать
бесконечный цикл.

Вызов внешнего provider — платёжной, почтовой или другой системы — образует
особую границу. Подключение к нему описывает connection: адрес, способ
аутентификации и конфигурацию. Входящее событие provider обрабатывает trigger —
правило, которое проверяет подлинность сообщения, подавляет дубликаты и ставит
в очередь соответствующую задачу. Продуктовая логика снова остаётся в service,
а connection и trigger отвечают за надёжный транспорт.

## Когда нужна долговременная последовательность

Для одной повторяемой задачи очереди достаточно. Многошаговый процесс, который
ждёт внешние события и должен переживать перезапуск приложения, оформляется как
durable workflow. Такой workflow сохраняет, какие шаги уже подтверждены, какие
данные получены и какого события система ожидает дальше. После сбоя он
продолжает работу с последней сохранённой точки, а не начинает всю
последовательность заново.

Если завершённый шаг нельзя физически отменить, workflow предусматривает
компенсацию — отдельное действие, уменьшающее последствия сбоя. Например,
после неудачного оформления доставки система не «откатывает» уже проведённый
внешний платёж транзакцией базы, а запускает явный возврат.

Workflow нужен не для каждого обращения к provider. Если вызывающая сторона
ждёт ответ, операция укладывается в один запрос, а повтор не требует
сохранённого межшагового состояния, достаточно обычного service с защищённым
внешним вызовом. Иначе платформа превращает простое действие в сложный процесс
с ненужным хранилищем состояния.

## Как runtime остаётся наблюдаемым

Общий путь полезен только тогда, когда можно понять, что именно произошло.
Runtime должен связывать журналы, метрики и трассу выполнения общим ID запроса
или задачи. Тогда разработчик видит последовательность: какая операция выбрана,
какая permission сработала, какой row scope применён, какой service вызван и
где возникла ошибка.

Наблюдаемость не означает запись всех данных без разбора. Секреты, персональные
данные и платёжные реквизиты должны скрываться, а audit хранит продуктово
значимые действия отдельно от технического диагностического лога.

Публичные контракты runtime также нуждаются в версиях. Расширения и
сгенерированный код должны обращаться к стабильному API платформы, а не к её
внутренним функциям. Иначе любое внутреннее улучшение ядра становится
ломающим изменением для всех проектов.

## Как runtime помогает агенту

Единый путь сокращает число мест, которые агент должен изменить. Чтобы добавить
обычный ресурс, достаточно декларации и стандартных политик; чтобы добавить
уникальную операцию, агент реализует service и подключает его через публичный
контракт runtime. Архитектурная форма перестаёт зависеть от того, какой файл
агент случайно нашёл первым.

Но runtime не подтверждает правильность бизнес-правила. Успешная регистрация
операции показывает, что платформа может её вызвать; корректность инварианта
доказывается спецификацией и тестами проекта. Для внешнего provider требуется
также фактическая проверка взаимодействия, а не только mock — управляемая
тестовая замена внешней системы с заранее заданными ответами.

## Цена общей точки исполнения

Runtime намеренно влияет на множество ресурсов, поэтому ошибка в его порядке
проверок имеет широкий радиус воздействия. Обновление требует совместимости,
наблюдаемости и постепенной миграции потребителей. Чем больше скрытых действий
происходит автоматически, тем труднее объяснить поведение и локализовать сбой.

Хорошая платформа удерживает в runtime только доказанно общую механику и
оставляет явный выход в проектный код. Если policy используется одной
операцией, требует множества исключений или выражает уникальное продуктовое
решение, её следует перенести во владеющий service.

Runtime можно применять самостоятельно. Когда же статические файлы и
исполняемые правила должны исходить из одной декларации, появляется отдельная
модель — [«Шаблонизатор с runtime»](03_Шаблонизатор_с_runtime.md).
