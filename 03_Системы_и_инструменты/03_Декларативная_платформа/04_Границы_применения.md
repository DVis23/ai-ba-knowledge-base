# Границы декларативной платформы

**Статус:** основной.

| Ситуация | Подход |
|---|---|
| Нужен начальный каркас | Одноразовый шаблонизатор |
| Артефакты регулярно пересобираются из схемы | Повторяемый шаблонизатор |
| Поведение определяется метаданными во время работы | Runtime |
| Нужны типы, SDK и общие исполняемые политики | Шаблонизатор с runtime |
| Почти всё поведение уникально | Обычный проектный код |
| Типовая модель требует множества исключений | Точка расширения или отказ от абстракции |

## Признаки хорошей границы

- декларация короче и понятнее заменяемого кода;
- сгенерированные области имеют одного владельца;
- уникальные правила видны в проектном коде;
- runtime предоставляет публичные точки расширения;
- обновление имеет описанную совместимость и миграцию;
- поведение можно диагностировать от входа до результата.

## Антипаттерны

**Генерация продуктового смысла.** Техническая схема не должна сама решать, что
разрешено пользователю.

**Скрытая логика шаблона.** Условия, влияющие на бизнес-результат, нельзя
прятать внутри генератора.

**Универсальная конфигурация.** Попытка выразить любое поведение флагами создаёт
новый язык без инструментов обычного языка программирования.

**Проектное правило в runtime.** Общее ядро не должно знать особенности одного
продукта.

**Неясное происхождение поведения.** Разработчик должен понимать, что было
сгенерировано, что интерпретируется runtime и какой код принадлежит проекту.
