# Шаблонизатор с runtime

**Статус:** концептуальный.

## Зачем связывать два независимых механизма

Шаблонизатор и runtime решают разные задачи. Первый до запуска приложения
создаёт согласованные файлы, второй во время работы исполняет общие политики.
Их можно применять отдельно. Связка нужна только тогда, когда статический
контракт и реальное поведение должны исходить из одной модели.

Например, клиентский SDK может быть сгенерирован с методом обновления заказа.
Если runtime не зарегистрировал такую операцию или ожидает другой набор полей,
клиент получает технически корректный, но неработающий интерфейс. Общая
декларация устраняет этот разрыв: генератор создаёт обещание для клиента, а
runtime читает те же факты и обеспечивает обещанное поведение на сервере.

```text
Resource: Order
  fields + relations + policies + operations
                    │
       ┌────────────┴────────────┐
       ↓                         ↓
генератор                    runtime registry
       ↓                         ↓
типы, миграция, API, SDK     CRUDL, права, audit, tasks
       └────────────┬────────────┘
                    ↓
          проектные services и UI
```

Связка является не «более развитым шаблонизатором», а отдельной архитектурной
моделью. Она добавляет долговременный контракт между созданным кодом и
исполняющей платформой, поэтому требует совместимости, миграций и диагностики,
которых нет у одноразовой генерации.

## Что именно становится общим источником

Декларация ресурса содержит только факты, нужные обеим сторонам: устойчивое имя,
поля, типы, связи, доступные операции и общие политики. Генератор использует
эту модель для схемы хранения, API-контракта, SDK и стандартного UI. Runtime
регистрирует ресурс, проверяет права и выполняет разрешённые CRUDL-операции —
создание, чтение, изменение, удаление и получение списка.

Общим должен быть именно смысл технического контракта, а не копия его внешнего
вида. Генератору TypeScript нужен синтаксис клиентского типа, runtime —
валидатор серверного входа, а базе — миграция столбца. Все три представления
различаются по форме, но получают одинаковый нормализованный факт: например,
`delivery_at` является необязательным моментом времени и доступен для записи
только в определённых операциях.

Runtime собирает декларации в registry — каталог известных ресурсов, операций
и политик. Registry является исполняемым снимком модели: по нему платформа
находит нужное поведение при запросе. Генерируемые файлы являются статическим
снимком той же модели: они используются компилятором языка, миграцией или
клиентским приложением ещё до первого запроса.

Из этого следует важная проверка. Совпадение текста декларации недостаточно;
нужно убедиться, что и генератор, и runtime интерпретировали её одинаково.
Иначе формально общий источник порождает два разных контракта.

## Как обеспечивается совместимость версий

Сгенерированный адаптер должен обращаться только к публичному API runtime —
стабильным функциям и типам, предназначенным для использования проектами. Его
нельзя связывать с внутренним методом ядра, который разработчики платформы
могут изменить без сохранения совместимости.

Версия генератора указывает диапазон версий runtime, с которыми совместим
результат. Такая запись образует контракт версий. Он отвечает не на вопрос
«какая версия новее», а на вопрос «понимает ли этот runtime форму и соглашения
сгенерированного кода».

Если меняется смысл декларации или публичный API, обновление проходит явно:

1. Миграция преобразует старую форму декларации в новую.
2. Генератор пересоздаёт статические артефакты.
3. Runtime проверяет registry по новым правилам.
4. Тесты подтверждают, что клиентское обещание совпадает с реальным вызовом.

Миграция здесь означает управляемый переход между версиями модели. Она может
изменять не только базу данных, но и имя поля декларации, форму политики или
контракт операции. Если старый и новый runtime некоторое время работают
одновременно, публичный контракт должен поддерживать обе стороны либо иметь
явный период несовместимости и порядок развёртывания.

## Что платформа создаёт, а что оставляет проекту

Декларация хорошо описывает повторяемые поверхности. Из ресурса можно получить
стандартную таблицу и форму админки, но сложный рабочий экран с собственным
состоянием и пользовательским сценарием остаётся проектным UI. Из описания
операции можно получить типы запроса и маршрутизацию, но расчёт, транзакционный
инвариант и интеграционная последовательность остаются в project service или
workflow.

Service — именованный модуль, который владеет уникальной бизнес-операцией.
Транзакционный инвариант — правило, которое должно оставаться истинным после
всех изменений базы в этой операции. Workflow нужен, когда многошаговый
процесс должен сохранять своё состояние между запросами и ожиданием внешних
событий.

Платформа подключает такой код через точки расширения с явными входами и
выходами. Внутри одной предметной области их удобно собирать в extension —
подключаемый модуль, содержащий ресурсы, services, операции, задачи,
интеграции, миграции и UI-разделы. Ядро видит только публичные контракты
extension, поэтому необязательная возможность не становится скрытой
зависимостью каждого проекта.

Эта граница также определяет направление зависимостей. Проектный service может
использовать публичные возможности runtime, но ядро платформы не должно знать
о заказах, скидках или доставке. Иначе обновление одного продукта потребует
менять общее ядро и затронет всех его потребителей.

## Как система проверяет собственную согласованность

Общая декларация снижает вероятность расхождения, но не устраняет её
автоматически. Ошибку может внести устаревшая генерация, ручная миграция,
несовместимая версия runtime или неверный адаптер. Поэтому проверка идёт в
несколько этапов.

Сначала registry валидирует внутреннюю модель: имена должны быть уникальны,
ссылки — вести к существующим ресурсам, а набор политик — быть совместимым с
типом операции. Ошибка останавливает запуск до того, как приложение начнёт
обслуживать запросы с частично собранной конфигурацией.

Затем система сравнивает независимые снимки:

- storage snapshot описывает фактические таблицы, столбцы, индексы и
  ограничения хранилища;
- contract snapshot описывает публичные ресурсы, поля, операции и права,
  которые видят клиенты.

Два снимка нужны потому, что хранение и публичный контракт изменяются не
одновременно. Новый индекс базы может не менять API, а новая версия операции
может использовать прежние таблицы. Объединённый снимок скрыл бы, в какой
именно области возникло расхождение.

Drift-план сравнивает ожидаемые снимки с фактическим состоянием. Drift означает
расхождение декларации и её производного результата. План перечисляет нужные
переходы и отдельно отмечает потенциально ломающие изменения — удаления,
переименования и сужение допустимых значений, которые способны нарушить работу
существующего клиента или потерять данные. Такие шаги требуют review —
осознанной проверки человеком последствий и плана перехода.

Не все архитектурные нарушения видны в декларации. Поэтому архитектурный
линтер анализирует обычный код и ищет обход установленной границы: бизнес-логику
в HTTP-адаптере, прямой вызов внутреннего API runtime, внешний запрос внутри
открытой транзакции или ручное дублирование общей политики. Линтером называется
автоматическая статическая проверка кода без запуска приложения.

В существующем проекте нарушения можно сначала зафиксировать в baseline —
исходном списке известного долга. Новые отклонения после этого блокируются, а
старые остаются видимыми и исправляются постепенно. Baseline не объявляет долг
правильной архитектурой; он отделяет уже известную проблему от новой
регрессии — нарушения, которое появилось после принятой исходной точки.

## Как связка помогает агенту

Агенту не приходится восстанавливать архитектуру чтением всех файлов. По
registry он видит ресурс, его операции и политики; по декларации — статические
поверхности; по extension — место уникальной логики. После изменения одного
источника генератор показывает patch, drift-план выявляет несовместимость, а
линтер проверяет границы.

Короткий цикл обратной связи уменьшает число решений, которые агент должен
угадать. Однако платформа не получает власть над требованиями. Спецификация
определяет нужный продуктовый результат, декларация описывает повторяемую часть
реализации, project service выражает уникальное правило, а тесты проверяют
наблюдаемое поведение.

Успешная генерация, собранный registry и чистый линтер вместе подтверждают
техническую согласованность, но не доказывают, что продуктовая семантика выбрана
верно. Если правило не следует из утверждённого требования, общая модель лишь
быстрее и последовательнее распространит ошибку по всем слоям.

## Главный предел связки

Чем больше потребителей у декларации, тем опаснее превращать её в универсальное
описание всей системы. Признак потерянной границы — флаги и вложенные исключения,
которые нужны одному ресурсу, но меняют генератор, runtime и схему для всех.
Декларация становится скрытым языком программирования без прозрачного потока
управления и локальной диагностики.

В такой ситуации общей модели оставляют устойчивые факты — поля, связи,
операции и действительно общие политики. Уникальное условие переносят в
обычный код с именованным интерфейсом и сфокусированными тестами. Платформа
должна уменьшать число мест, где выражена одна и та же механика, а не уменьшать
видимость продуктового правила.
