# Шаблонизатор с runtime

**Статус:** концептуальный.

Связка нужна, когда одна и та же модель должна согласовать подготовку проекта и
его дальнейшее исполнение. Шаблонизатор создаёт статические поверхности, а
runtime читает ту же декларацию и реализует обещанное ими поведение.

## Сквозной путь декларации

```text
Resource: Order
  fields + relations + policies + operations
                    │
       ┌────────────┴────────────┐
       ↓                         ↓
генератор                    runtime registry
       ↓                         ↓
типы, миграция, API, SDK     CRUDL, права, audit, tasks
       └────────────┬────────────┘
                    ↓
          проектные services и UI
```

Декларация ресурса задаёт факты, нужные обеим сторонам: имя, поля, связи,
доступные операции и общие политики. Генератор использует их, чтобы создать
типы, миграцию и клиентский SDK. Runtime регистрирует тот же ресурс и применяет
политики при реальном вызове. Благодаря общему источнику клиентский метод не
обещает поле или операцию, которых backend не знает.

Связь работает только при явном контракте версий. Сгенерированный адаптер
обращается к публичному API runtime, а не к его внутренним функциям. Версия
генератора записывает, с какими версиями runtime совместим результат. Если
контракт меняется, миграция обновляет декларацию и производные артефакты явно.

## Что остаётся проекту

Из декларации можно получить стандартную форму админки, но сложный рабочий
экран остаётся проектным UI. Из неё можно получить контракт операции, но
расчёт, транзакционный инвариант и интеграционная последовательность остаются в
service или workflow проекта.

Платформа вызывает этот код через точки расширения. Расширение одной предметной
области может собрать ресурсы, services, операции, задачи, интеграции, миграции
и UI-разделы. Ядро видит только публичные контракты расширения, поэтому
опциональная возможность не становится зависимостью всех проектов.

## Как система обнаруживает собственные расхождения

Общий источник не гарантирует согласованность сам по себе. Перед запуском
registry проверяет уникальность имён, существование связей и совместимость
политик. Затем система сравнивает два независимых снимка:

- storage snapshot отражает таблицы, столбцы, индексы и ограничения;
- contract snapshot отражает публичные ресурсы, поля, операции и права.

Разделение необходимо: внутренняя миграция базы может не менять API, а новая
версия операции может не затрагивать хранение. Drift-план сравнивает ожидаемые
снимки с фактическим состоянием и помечает потенциально ломающие изменения для
review.

Архитектурный линтер дополняет эту проверку там, где деклараций недостаточно.
Он обнаруживает бизнес-логику в транспортном адаптере, ручной обход общей
политики или внешний вызов внутри транзакции. Baseline позволяет сначала
зафиксировать старый долг, а затем запрещать новые нарушения.

## Почему такая платформа удобна агенту

Агенту не нужно восстанавливать устройство проекта чтением всех файлов. Он
может запросить registry ресурса, путь операции и вероятных потребителей
контракта. После изменения декларации генератор показывает patch, drift-план и
результат линтера. Короткая обратная связь ограничивает число архитектурных
решений, которые модель вынуждена угадывать.

Это не передаёт платформе власть над требованиями. Спецификация отвечает,
какой результат нужен; декларация показывает повторяемую часть реализации;
проектный код выражает уникальное правило; тесты проверяют итог.

## Главный предел связки

Одна декларация легко превращается в скрытый язык программирования. Признак
проблемы — флаги и вложенные исключения, используемые только одной функцией.
Тогда генератору и runtime оставляют общую механику, а условие переносят в
обычный код с именованным интерфейсом и тестами.
