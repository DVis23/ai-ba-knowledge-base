# Шаблонизатор приложений

**Статус:** концептуальный.

Шаблонизатор решает задачу, которая возникает до запуска приложения: как один
раз описать повторяемую структуру и стабильно получить из неё множество
согласованных файлов. Например, описание сущности заказа может породить модель
данных, API-схему, форму админки и клиентские типы. Без общего источника эти
представления приходится синхронизировать вручную.

## Как описание превращается в файлы

```text
декларация заказа
      ↓ проверка формы
нормализованная модель
      ↓ выбор шаблонов
модель + API-схема + миграция + SDK
      ↓ сравнение с предыдущим результатом
patch для проекта
```

На входе находится декларация — компактное описание того, чем один ресурс
отличается от другого: его поля, связи и доступные поверхности. Сначала
генератор проверяет декларацию по схеме. Без этого опечатка в типе поля может
дать четыре взаимно несовместимых файла.

После проверки генератор приводит вход к внутренней модели. На этом шаге
подставляются явные defaults и разрешаются ссылки между ресурсами. Только затем
шаблоны превращают модель в файлы конкретного стека. Разделение внутренней
модели и шаблонов позволяет одной декларации порождать Python-код и TypeScript
SDK без копирования бизнес-описания.

Миграция занимает особое место. Текущая декларация описывает желаемое
состояние, но существующая база содержит данные в предыдущем состоянии.
Генератор может предложить преобразование, однако потенциально разрушающий шаг
— удаление столбца или изменение смысла значения — требует review.

## Одноразовая и повторяемая генерация

В одноразовом режиме шаблонизатор создаёт стартовый каркас. После создания
файлы полностью переходят проекту, и генератор больше не обязан понимать их
ручные изменения. Этот режим полезен, когда повторяется только начальная
структура пакета.

В повторяемом режиме декларация продолжает владеть генерируемой областью.
Изменение описания снова запускает генератор и создаёт предсказуемый patch.
Одинаковый вход должен давать одинаковый результат; иначе обычный повтор
команды создаёт шумный diff и уничтожает доверие к системе.

Повторяемость порождает проблему владения. Если человек изменит файл, который
генератор затем пересоздаёт, возникнет drift — расхождение декларации и её
производного результата. Поэтому система должна явно разделять:

- полностью генерируемые файлы;
- проектные файлы, которыми генератор не владеет;
- предусмотренные точки расширения между ними.

Точка расширения позволяет проекту добавить уникальную реализацию через
стабильный интерфейс. Она лучше ручных вставок внутрь шаблона: при обновлении
генератора граница остаётся видимой и проверяемой.

## Где заканчивается шаблонизатор

Шаблонизатор фиксирует форму, но не принимает продуктовых решений. Он может
создать место для расчёта скидки и типы его входов, но само правило скидки
должно оставаться в проектном коде и ссылаться на утверждённое требование.

Если для каждого нового правила в шаблон добавляется очередной флаг и ветвление,
шаблон превращается в плохо оснащённый язык программирования. В этот момент
нужно оставить генератору повторяемую структуру, а уникальное поведение вернуть
обычному коду.
