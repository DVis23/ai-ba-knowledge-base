# Артефакты и schema workflow

После создания change недостаточно сложить в папку произвольные заметки. Нужно
развести вопросы, которые команда решает в разное время. Schema задаёт виды
артефактов, их зависимости и путь создания.

## От намерения к исполнимой работе

В стандартной `spec-driven` schema поток выглядит так:

```text
proposal: зачем и в каких границах
      ├──────────────┐
      ↓              ↓
delta specs       design
что меняется      как это обеспечить
      └──────┬───────┘
             ↓
           tasks
      что выполнить и проверить
```

Proposal изменения тайм-аута объясняет проблему: неактивная сессия живёт дольше
допустимого, а пользователь теряет введённые данные без предупреждения. Он
задаёт scope — истечение и предупреждение — и явно оставляет за границей общую
переработку аутентификации.

Из intent возникают два разных вопроса. Delta spec формулирует наблюдаемое
обязательство: когда появляется предупреждение и когда сессия прекращается.
Design решает, откуда берётся время, как синхронизируются вкладки и какой
компонент отзывает токен. Смешение этих вопросов делает внутреннюю реализацию
частью продукта и затрудняет последующую замену.

Tasks создаются после требований и design, потому что должны реализовать уже
понятный результат выбранным способом. Зависимость не делает workflow
необратимым. Если во время реализации обнаружен конфликт часов клиента и
сервера, команда возвращается к design, а при изменении пользовательского
результата — к delta spec.

## Как schema управляет созданием

Schema хранит для каждого артефакта путь результата, template, instructions и
`requires`. Template задаёт стабильную форму Markdown, а instructions объясняют,
какой смысл в неё помещать. Форма без инструкции порождает аккуратные пустые
документы; инструкция без формы раскладывает одинаковый смысл по разным местам.

Концептуально стандартная схема выглядит так:

```yaml
artifacts:
  - id: proposal
    generates: proposal.md
    requires: []
  - id: specs
    generates: specs/**/*.md
    requires: [proposal]
  - id: design
    generates: design.md
    requires: [proposal]
  - id: tasks
    generates: tasks.md
    requires: [specs, design]
```

Конкретная установленная schema может отличаться: design бывает необязательным,
а проект может добавить собственный артефакт. Поэтому команды читают project
config и metadata change, а не предполагают структуру по памяти.

Локальный `.openspec.yaml` делает отклонение видимым внутри change. Несколько
schema в одном проекте оправданы только тогда, когда команда готова объяснить,
почему одинаковая команда создаёт разные наборы документов.
