# Frontend, backend и UI-источники

OpenSpec одинаково описывает наблюдаемое поведение frontend и backend, но путь
к requirement различается. Для интерфейса часть контракта уже выражена
визуально; для backend основными входами становятся правила, состояния данных и
внешние протоколы.

## Как макет дополняется спецификацией

Макет показывает состав, иерархию, labels, расположение контролов и визуальные
состояния. Переписывание этих деталей в Markdown создаёт вторую дизайн-систему,
которая быстро устаревает.

Spec добавляет только semantic overlay — смысл, которого нельзя надёжно вывести
из картинки. Для предупреждения о тайм-ауте это источник времени, момент
появления, доступные действия, поведение нескольких вкладок и результат при
ошибке продления. Layout и цвет остаются в макете или коде.

Если экранов и вариантов много, проект может завести промежуточную Screen Spec:
сопоставить фреймы, состояния, динамические поля и переходы. Это локальная
надстройка, а не обязательный артефакт OpenSpec. Демонстрационное значение в
макете показывает форму, но не становится бизнес-числом. Неясная скрытая часть
интерфейса превращается в вопрос, а не достраивается агентом.

## Как тот же результат выражается на backend

Backend обеспечивает истечение сессии независимо от того, открыт ли экран.
Его requirement описывает обязательство потребителя: вход, результат,
значимые ошибки, область доступа, повтор вызова, конкуренцию и внешние эффекты.

Конкретный endpoint, DTO, таблица и библиотека обычно относятся к design. Они
попадают в requirement только тогда, когда сами являются публичным контрактом.
Например, формат внешнего события важен потребителю; имя внутреннего класса —
нет.

Frontend и backend delta могут находиться в одном change, если обеспечивают
один пользовательский исход. Общее правило времени хранится в одной capability,
а потребители ссылаются на него. Такое разделение не позволяет двум слоям
независимо выбрать разные значения.

## Что не нужно специфицировать заново

Стандартные loading-состояния, поведение браузера и типовая механика платформы
не становятся requirements, если функция их не меняет. Спецификация фиксирует
проектное отличие: особую доступность действия, нестандартную деградацию или
обязательный пользовательский результат.
