# Стадия 3. Спеки и архитектура

БА-документация говорит, чего хочет бизнес. Эта стадия переводит её в то, что потребляет код. Важно сразу: спека и архитектура — **не два обязательных слоя подряд**. Это набор задач, которые разные фреймворки покрывают по-разному и с пересечением. Сначала — задачи, потом — чем их закрыть.

## Что нужно получить (задачи, не фреймворки)

Эти задачи существуют независимо от того, какой фреймворк выберешь:

|Задача|Что фиксирует|Когда|
|---|---|---|
|**Поведение (WHAT)**|`Requirement` + `Scenario`, приёмочные критерии|всегда|
|**Технический контракт (HOW)**|endpoint / DTO / auth / события|когда есть что проектировать|
|**Архитектурная рамка**|границы, зависимости, ключевые ADR|один раз на приложение/систему|
|**UI**|экраны, состояния|только фронтенд|
|**Единица работы для ИИ**|capability / Behavior Slice|перед кодингом|

## Спека и архитектурный фреймворк: пересекаются, чаще альтернативы

Оба — документная семья, оба потребляют БА как источник истины, и **оба покрывают поведение + контракт**. Это не «WHAT-фреймворк» и «HOW-фреймворк» — они во многом делают одно и то же. Различает их обвязка:

|Фреймворк|Что несёт сверх ядра|На чём силён|
|---|---|---|
|[**OpenSpec**](../03_Фреймворки/04_Спеки.md)|capability, `design.md`, **дельты и жизненный цикл изменений**|backend/сервисы/API, эволюция существующего (brownfield), поведенческие контракты|
|[**Архитектурный фреймворк**](../03_Фреймворки/05_Архитектурный_фреймворк.md)|Overview/Boundaries/ADR + State Machine + **Behavior Slice с `implementationHints`**|клиентские приложения (mobile/FE), новый продукт, UI-состояния, нарезка для ИИ|

На ядре (поведение + контракт) они **взаимозаменяемы** — берёшь один, не оба. У архитектурного фреймворка своя поведенческая спека (Feature Spec) уже внутри, отдельный OpenSpec ему не нужен; и наоборот, для backend-сервиса хватает OpenSpec без мобильной арх-документации.

## Как выбрать или скомбинировать

|Случай|Чем закрыть|
|---|---|
|Backend-сервис, API, правка существующего|OpenSpec|
|Клиентское приложение, новый продукт, нужны UI-состояния и срезы|архитектурный фреймворк|
|Большая система из подсистем|рамка (границы/ADR) один раз + backend через OpenSpec, app через архитектурный — комбинируешь, не дублируешь|
|Маленькая фича|одна поведенческая спека, без архитектурной рамки|

Комбинируют по разделению труда, а не «оба ради полноты»: архитектурная рамка из одного фреймворка + поведенческие спеки из другого. Дублировать поведение в двух форматах — антипаттерн.

## Граница, которая держится всегда

Независимо от фреймворка, не путай слои:

- **Поведение и правило** → `Requirement`/`Scenario` (или Feature Spec). Числа и пороги — из `BR`/`BD` БА, не из кода и не из агрегатора.
- **Endpoint / DTO / auth** → `design.md` или API-контракты, **не** в тексте поведения.
- **Пиксели и тексты UI** → Screen Spec (фронтенд).

## Порядок

БА — всегда первой: спека цитирует решения и правила, а не код или догадку. Внутри стадии порядок не «спека, затем архитектура», а: поставь архитектурную рамку один раз (если приложению она нужна), дальше по каждой фиче — поведение (+ контракт, + UI для FE), выбранным фреймворком. Код — следующей стадией; в спеке он прототип, не источник.

## Трассировка

Спека цитирует БА (`Trace: BD-02 §2.5, BR-10`), код цитирует спеку (`@trace: F-04, BR-10`). Код в спеке — прототип, не источник: в строках реализации ставится `TRACE-GAP`, целевой контракт выводится из решений. Так запрос `impact` к графу проходит сквозь спеки до кода.
