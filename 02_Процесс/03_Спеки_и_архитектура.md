# Стадия 3. Спеки и архитектура

БА-документация говорит, чего хочет бизнес. Эта стадия переводит её в то, что потребляет код. Важно сразу: спека и архитектура — **не два обязательных слоя подряд**. Это набор задач, и основной инструмент, который их закрывает, — [фреймворк спек (OpenSpec)](../03_Фреймворки/04_Спеки.md). Архитектурный фреймворк — справочная альтернатива, в бою не применялся. Сначала — задачи, потом — чем их закрыть.

## Что нужно получить (задачи, не фреймворки)

Эти задачи существуют независимо от того, какой фреймворк выберешь:

|Задача|Что фиксирует|Когда|
|---|---|---|
|**Поведение (WHAT)**|`Requirement` + `Scenario`, приёмочные критерии|всегда|
|**Технический контракт (HOW)**|endpoint / DTO / auth / события|когда есть что проектировать|
|**Архитектурная рамка**|границы, зависимости, ключевые ADR|один раз на приложение/систему|
|**UI**|экраны, состояния|только фронтенд|
|**Единица работы для ИИ**|capability / Behavior Slice|перед кодингом|

## Основной путь: спеки (OpenSpec)

Все задачи стадии, кроме архитектурной рамки, закрывает [OpenSpec](../03_Фреймворки/04_Спеки.md) — обкатан в бою и на backend, и на фронтенде:

|Задача|Чем закрыта|
|---|---|
|Поведение|`spec.md`: `Requirement` + `Scenario` по capability|
|Технический контракт|`design.md` — endpoint/DTO/auth из решений, не из кода|
|UI (фронтенд)|Screen Spec → OpenSpec (FE-трек)|
|Единица работы для ИИ|capability + `tasks.md` изменения|
|Эволюция существующего|дельты `changes/`: Propose → Review → Apply → Archive|

**Архитектурная рамка** (границы системы, ключевые ADR) в OpenSpec не живёт. Она ставится один раз, отдельными документами — обзор и ADR рядом с корпусом БА, — и дальше цитируется спеками. Второй фреймворк ради неё не берут.

## Архитектурный фреймворк: справочная альтернатива

[Архитектурный фреймворк](../03_Фреймворки/05_Архитектурный_фреймворк.md) покрывает то же ядро (поведение + контракт) для клиентских приложений: Feature Spec, Screen State Machine, Behavior Slice с `implementationHints`. В этом методе он **пока не применялся** — глава о нём в базе в осведомительном ключе.

Что заимствовать уже сейчас, оставаясь на OpenSpec: нарезку работы на вертикальные срезы и подсказки реализации (пути файлов, имена классов, зависимости) в пакете задачи для ИИ. Брать его целиком вместо OpenSpec имеет смысл, только если проект — клиентское приложение, где UI-состояния нужны как первоклассный артефакт. Дублировать поведение в двух форматах — антипаттерн: на ядро берёшь один фреймворк.

## Как это выглядит в бою: два рукава

Формат спеки один, а путь к ней зависит от того, что появилось раньше — канон или экран:

|Рукав|Путь|Особенность|
|---|---|---|
|**Бэкофис / web**|БА-корпус → прототип интерфейса → **диктовка поверх живого экрана** (сырые критерии, RAC) → сведение трёх слоёв (БА + прототип + диктовка) → канонический AC в спеке|конфликты слоёв решает владелец продукта явно|
|**Мобильное приложение**|дизайн и вёрстка первыми → диктовка поведения → AC напрямую в спеку|источник трассы — диктовка и дизайн, слой RAC пропускается|

Сырой критерий (RAC) — человеческий первоисточник; канонический AC — его нормализация. Связь «AC нормализует RAC» остаётся в графе: приёмка трассируется до слов человека. Прототип и существующий код в обоих рукавах — наблюдения, не источники: расхождение помечается `TRACE-GAP` и закрывается правкой канона.

## Валидация: два слоя проверок

|Слой|Инструмент|Ловит|
|---|---|---|
|**Форма**|валидатор спек (`validate --strict`)|структуру: Requirement без Scenario, сломанные дельта-заголовки|
|**Связность**|[граф-инструмент](../03_Фреймворки/02_Граф.md): `lint <ID>`, `coverage`, `gate`|висячие Trace-ID, AC без тест-доказательства, разрывы покрытия|

Плюс approval-gate человеком: согласование «ЧТО/AC» до начала кода — единственная проверка, которую нельзя автоматизировать.

## Граница, которая держится всегда

Независимо от фреймворка, не путай слои:

- **Поведение и правило** → `Requirement`/`Scenario` (или Feature Spec). Числа и пороги — из `BR`/`BD` БА, не из кода и не из агрегатора.
- **Endpoint / DTO / auth** → `design.md` или API-контракты, **не** в тексте поведения.
- **Пиксели и тексты UI** → Screen Spec (фронтенд).

## Порядок

БА — всегда первой: спека цитирует решения и правила, а не код или догадку. Внутри стадии порядок не «спека, затем архитектура», а: поставь архитектурную рамку один раз (если приложению она нужна), дальше по каждой фиче — поведение (+ контракт, + UI для FE), выбранным фреймворком. Код — следующей стадией; в спеке он прототип, не источник.

## Трассировка

Спека цитирует БА (`Trace: BD-02 §2.5, BR-10`), код цитирует спеку (`@trace: F-04, BR-10`). Код в спеке — прототип, не источник: в строках реализации ставится `TRACE-GAP`, целевой контракт выводится из решений. Так запрос `impact` к графу проходит сквозь спеки до кода.
