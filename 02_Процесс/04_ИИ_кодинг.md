# Стадия 4. ИИ-кодинг

Спеки и архитектура → работающий код. Здесь стохастичность LLM опаснее всего, поэтому контракт уходит в сам код: кодовая семья фреймворка ([код-фреймворк](../03_Фреймворки/06_Код_фреймворк.md)) убирает boilerplate, оставляя ИИ только сложную бизнес-логику.

## Единица работы для ИИ

Не «вся фича», а минимальный вертикальный срез с приёмочным критерием — **Behavior Slice** (или capability спеки). Почему именно он годится для ИИ:

- завершён (одно поведение целиком), проходит через все слои;
- наблюдаемый результат → можно проверить тестом;
- маленький scope → влезает в контекст, закрывается за один проход;
- несёт Implementation Hints: точные пути файлов, имена классов, зависимости, структуру тестов.

ИИ получает узкий пакет задачи, а не репозиторий.

## Код-фреймворк убирает boilerplate

Водораздел: **«сохрани строку» генерит фреймворк, «сделай что-то» пишет ИИ**.

|Генерит фреймворк|Пишет ИИ руками|
|---|---|
|CRUD, фильтры, пагинация, admin-метаданные|расчёты, чекаут, доменные инварианты|
|REST-эндпоинты, миграции, OpenAPI/типы|импорт/экспорт, адаптеры провайдеров|
|RBAC, audit, idempotency|кастомные команды, вебхуки|

ИИ не пишет код, который плывёт от прогона к прогону, — его генерит детерминированно из декларации. Как устроен такой фреймворк и как собрать свой → [06_Код_фреймворк](../03_Фреймворки/06_Код_фреймворк.md).

## Тесты первыми

Порядок внутри единицы работы — TDD от приёмочных критериев: из AC спеки пишутся **красные тесты**, затем реализация до зелёных. Тест именуется и трассируется к AC — так он становится тест-доказательством в [графе](../03_Фреймворки/02_Граф.md): `gate` изменения видит, какой критерий покрыт, а какой нет. Код без красного теста впереди — это код, чью цель никто не зафиксировал.

## Двухагентное исполнение

Единицу работы закрывает цикл из двух ролей: **агент-исполнитель** реализует один пункт (`tasks.md` изменения или один Gap), **агент-ревьюер** в отдельной сессии проверяет результат против спеки и конвенций, человек утверждает. Ревьюер без контекста исполнителя не наследует его заблуждений — дешёвая замена парного программирования для ИИ.

## Проверка вывода ИИ

Форма кода проверяется машинно, не на глаз:

|Механизм|Что ловит|
|---|---|
|Компилятор / типы|несоответствие контракту|
|Drift-checks|декларация разошлась с БД / OpenAPI / admin|
|Архитектурный линтер|бизнес-логика в роутере, ручной аудит, транзакция поверх внешнего вызова|
|Контракт-тесты|нарушено поведение из спеки|
|`AGENTS.md` / `CLAUDE.md`|операционный контракт: команды, границы, когда уходить в кастом|

`AGENTS.md` держит ИИ в рамках так же, как схема артефакта держит его в БА: без него модель каждый раз изобретает структуру заново.

## Трассировка обратно

Три канала, которыми код виден графу:

- **`@trace`-комментарии**: `// @trace: AC-CART-014, BR-10` — ссылка на AC и правило; skill `ba-check-code-impact` проверяет, что у каждого `@trace` есть живой артефакт-источник.
- **Observed-слой**: [код-фреймворк](../03_Фреймворки/06_Код_фреймворк.md) экспортирует свои декларации (ресурсы, методы, jobs) в граф как узлы реализации — факт «ресурс существует» попадает в граф из кода, а не со слов.
- **UI-трассировка**: стабильные test-id элементов интерфейса + сайдкар-карта «элемент → AC», консистентность которой проверяет тест.

Так замыкается цикл: `impact BD-02` проходит от решения встречи через правила и спеки до файлов кода и тестов.

## Обратная связь из эксплуатации

Демо, раскатка и багрепорты возвращают знание в канон: наблюдение → канон-правка спеки (или новое решение `BD`) → код. Правка кода без правки канона — расхождение, которое граф покажет как дрифт; молчаливое «подгоним доку под код» — запрещённый ход, у канона есть владелец.

## Когда строить свой фреймворк

Документные фреймворки (стадии 1–3) переиспользуешь как есть. Код-фреймворк привязан к стеку: готовый под твой стек редко подходит. Тогда фулл-стек ИИ-специалист собирает его сам — это замыкающая компетенция всего цикла: [как построить код-фреймворк](../03_Фреймворки/06_Код_фреймворк.md).

Назад к карте: [Полный цикл](../01_Концепция/03_Полный_цикл.md).
