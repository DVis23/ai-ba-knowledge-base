# Создание собственной агентной среды

**Статус:** концептуальное руководство.

Собственная среда нужна, когда готовый coding harness не поддерживает требуемые
модели, permissions, приватный контур, интерфейсы или продолжительные процессы.
Начинать нужно не с мультиагентности, а с одного проверяемого цикла.

## 1. Определить назначение

Нужно назвать задачи, которые среда выполняет, и результат, по которому они
считаются завершёнными.

Примеры разных назначений:

- read-only исследование репозитория;
- подготовка patch без применения;
- coding agent с тестами;
- агент сопровождения инцидента;
- обработчик документного workflow.

Одна среда может поддерживать несколько профилей, но каждый профиль имеет свой
набор tools и permissions.

## 2. Задать внутренние интерфейсы

До подключения провайдера фиксируются собственные типы:

```text
Message        роль + содержимое
ToolDefinition имя + описание + входная схема
ToolCall       имя + проверенные аргументы
Observation    статус + данные + ошибка
ModelRequest   сообщения + tools + ограничения
ModelResponse  текст + tool calls + usage
```

Внутренний контракт защищает систему от формата одного API. Provider adapter
берёт на себя перевод.

## 3. Реализовать минимальный цикл

Минимальная версия умеет:

1. принять цель;
2. собрать короткий контекст;
3. вызвать модель;
4. проверить tool call по схеме;
5. выполнить read-only инструмент;
6. вернуть observation модели;
7. остановиться с итогом или ошибкой.

Сначала достаточно чтения файлов и поиска. Запись, shell и сеть добавляются
после появления permissions и журнала действий.

## 4. Добавить filesystem seam

**Seam** — явная граница, через которую компонент взаимодействует с внешней
средой.

Файловый seam должен:

- нормализовать путь;
- запрещать выход из разрешённых корней;
- различать чтение, создание, изменение и удаление;
- возвращать patch для проверки;
- ограничивать размер читаемого файла.

## 5. Добавить командный executor

Команда исполняется с явным working directory, timeout и лимитом вывода.
Нельзя передавать модели неограниченный системный shell как единственный tool.

Безопаснее иметь отдельные операции: поиск, тест, package command и Git status.
Свободная команда остаётся escape hatch и получает более строгий approval.

## 6. Ввести permissions

Для каждого tool определяется режим:

- автоматическое выполнение;
- выполнение только после подтверждения;
- полный запрет.

Политика учитывает аргументы. Чтение файла и рекурсивное удаление каталога не
могут иметь одинаковое разрешение только потому, что оба используют filesystem.

## 7. Сохранять состояние

После каждого значимого шага сохраняются:

- цель и scope;
- выполненные действия;
- изменённые артефакты;
- результаты проверок;
- ожидаемое решение человека;
- следующий безопасный шаг.

Это позволяет возобновить задачу без пересказа всей истории модели.

## 8. Добавить project layer

Проектный слой подключает:

- постоянные инструкции репозитория;
- skills по типам задач;
- команды проверки;
- карту каталогов и владельцев;
- правила работы с dirty tree;
- источники продуктовой истины.

Эти правила хранятся рядом с проектом и версионируются вместе с ним.

## 9. Добавить наблюдаемость

Минимальная трасса содержит request ID, модель, длительность, tool calls,
approvals, изменённые файлы, проверки и итоговый статус.

Секреты, полное содержимое приватных файлов и чувствительные prompts не должны
попадать в лог по умолчанию.

## 10. Проверять среду через evals

Eval-набор должен включать:

- задачу, решаемую только чтением;
- безопасное изменение нескольких файлов;
- конфликт инструкций;
- попытку выйти из разрешённого каталога;
- запрос разрушительного действия;
- длинную задачу с возобновлением;
- ошибку tool и восстановление;
- смену модели через adapter.

Метрика «агент ответил» бесполезна. Проверяются правильность файлов, отсутствие
запрещённых действий, фактический запуск проверок и понятный итоговый отчёт.

## Порядок зрелости

```text
чат с tools
  → один агент с permissions
  → сохранение состояния и resume
  → project skills и evals
  → параллельные агенты
  → маршрутизация моделей
```

Следующий уровень добавляется только после наблюдаемой потребности. Оркестрация
не исправляет ненадёжный одиночный цикл; она размножает его ошибки.
