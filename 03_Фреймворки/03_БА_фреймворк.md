# БА-фреймворк

Документный фреймворк для бизнес-анализа: фиксирует бизнес-знание (решения, процессы, правила, домен) до перевода в спеки и код. Отвечает на ЧТО хочет бизнес и ПОЧЕМУ. Движок — [триада](01_Триада.md); ниже — что специфично для БА. Таксономия ниже — рабочий пример, который адаптируешь под свой проект.

## Типы артефактов

ИИ генерирует не код, а типизированные артефакты бизнес-знания. Каждый тип — своя роль, ID-схема и regex для графа. Типичный набор:

|Тип|Роль|ID-схема (пример)|
|---|---|---|
|`ST`|ожидания стейкхолдеров|`ST-\d{2}`|
|`BR.X`|требования (иерархия)|`BR\.\d+(\.\d+)?`|
|`BR-XX`|атомарные правила (формулы, пороги)|`BR-\d{2}`|
|`BP`|сквозные процессы (E2E)|`BP-\d{2}[a-z]?`|
|`BD`|решения (ADR-подобные)|`BD-\d{2}`|
|`BF`|функции — индекс, **не** источник чисел|`BF\.\d{2}\.\d+`|
|`F`|фичи (Gherkin/PRD)|`F-\d{2}`|
|`DM` / `EN` / `SM`|домен: сущности / справочники / статусные модели|`DM-\d+`, `EN-\d{2}`, `SM-\d{2}`|
|`M` / `RL`|модули / роли и права|`M\d{2}`, `RL-\d{2}`|

Две похожие схемы `BR.X` (требование, иерархия) и `BR-XX` (правило, плоское) — разные типы; regex с lookbehind/lookahead их разводит (см. [Граф](02_Граф.md)).

## Структура артефакта

Тип задаёт обязательные секции — это и есть «форма», которую фиксирует фреймворк. Примеры:

**Правило `BR-XX`:** Описание → Формула → Входные параметры (таблица с источником) → Выход → Нормативная ссылка → Применение (в каких `BP`) → Тест-кейсы.

**Решение `BD-XX`:** Контекст (кто, когда, почему) → Варианты → Принятое решение + обоснование → Последствия → Ревью и подписи (signed/draft).

Линтер графа проверяет наличие обязательных секций по типу (правила в конфиге графа).

## Конвенции

Сквозные правила всех BA-скиллов:

|Правило|Суть|
|---|---|
|**Стабильные ID**|уточнил смысл — тот же ID; сменил — новый, старый `Deprecated → …`|
|**Lint после правки**|пересобрать граф + `lint <ID>`; ERR чинить до завершения|
|**Dual mode**|skill работает на создание и на инкрементальное обновление|
|**Assume → mark**|догадка → `[ПРЕДПОЛОЖЕНИЕ]` + открытый вопрос + источник|
|**Бизнес-язык**|документы для заказчика: эффект для бизнеса первым, техника — переводом|
|**Единая терминология**|единый набор терминов для сторон проекта во всех артефактах|

## Где ценность

- **Single source of truth для правил и чисел.** Порог живёт в одном `BD`/`BR-XX`; процессы и спеки ссылаются, не копируют. `BF`-индекс и агрегаторы — **не** источник числа.
- **Трассируемость до источника.** Правило возводится к решению и к рафинату встречи: «`BR-10` — из `BD-02`, со слов заказчика, дата».
- **Decision capture.** ПОЧЕМУ зафиксировано отдельным `BD` — через месяц не перерешают.
- **Impact на сотнях артефактов.** `impact BD-02` → что протухнет при смене решения.

## Граница: где БА кончается

БА даёт **rule-source и domain-source** — правила, числа, сущности, роли. Он **не** описывает endpoint, DTO, состояния экрана, код — это забирает слой спеки. Мост БА → код — spec-driven: спека потребляет `BD`/`BR` как источник истины, код помечается `@trace`, оставаясь прототипом. Разбор → [Спеки](04_Спеки.md). Процесс генерации артефактов → [02_БА_документация](../02_Процесс/02_БА_документация.md).

Таксономия растёт вместе с проектом: на стадии спек к ней добавляется **приёмочный слой** — экранные критерии (`SC`), сырые критерии из диктовок (`RAC`), канонические `AC`, элементы UI — со своими ID-схемами и рёбрами в том же графе (`AC` нормализует `RAC`, тест верифицирует `AC`). Правила те же: стабильные ID, regex в конфиге графа, coverage-ожидания.
