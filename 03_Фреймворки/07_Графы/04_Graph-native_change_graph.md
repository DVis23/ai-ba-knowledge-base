# Graph-native change graph

## Назначение

Graph-native change graph превращает индекс в рабочую поверхность изменения.
Change получает стабильный ID, scope и связи с затрагиваемыми артефактами.
Граф компилирует контекст и остаток работ для агента.

```text
trace graph + change intent
  → bounded scope
  → graph slice
  → worklist
  → evidence plan
  → readiness findings
```

Разворот состоит не в новых типах узлов. Граф начинает участвовать в управлении
работой: определяет scope, предлагает следующий шаг и хранит состояние change.

## Единица изменения

До этой модели агент менял отдельный документ и запускал проверки. Теперь
единица работы — `CHG-*`, содержащий:

- цель;
- исходные человеческие источники;
- список или вычисляемый scope stable-ID артефактов;
- задачи;
- ожидаемые доказательства;
- lifecycle state.

Change импортируется как узел. `CONTAINS` связывает его с контрактными
артефактами. Входящие и исходящие рёбра ограничивают контекст, который получает
агент.

## Устройство

```text
change manifest / change folder
           │
           ├─ sources
           ├─ declared scope
           └─ lifecycle
                    │
                    ▼
        stable-ID semantic graph
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   graph slice    worklist    evidence plan
       │            │            │
       └────────────┴────────────┘
                    ▼
               change gate
```

### Graph slice

Срез содержит только сильные рёбра, scope и ограниченный контекст. Он заменяет
передачу модели всего репозитория.

Типичный узел среза включает:

- ID, тип и origin;
- выдержку содержания;
- входящие и исходящие сильные связи;
- вычисленные состояния;
- адрес определения.

### Worklist

Worklist выводится из gaps графа:

- отсутствующий canonical ID;
- контракт без реализации;
- критерий без тестовой трассы;
- открытая задача change;
- дрейф принятого артефакта.

Это детерминированный список структурных работ. Он не способен решить
продуктовый вопрос и не должен придумывать ответ.

### Evidence plan

`evidence-plan` классифицирует acceptance criteria и предлагает вид проверки:
unit, API/integration, UI/e2e или contract. Классификация опирается на типы и
политику проекта.

План является гипотезой о достаточном evidence. Человек или владеющий SDD
процесс должен подтвердить, что проверяется правильное поведение.

### Fingerprints

Fingerprint фиксирует содержание, сильные связи, observed facts и evidence.
Расхождение с принятым снимком даёт `stale`.

Механизм полезен для drift detection. Риск возникает, если совпадение снимка
принимается за подтверждение смысла.

## Lifecycle

Ранний workflow:

```text
create → compile → check → accept → archive
```

Git-native вариант использовал branch и semantic diff, но сохранял ту же
единицу: graph-native change со scope и fingerprint.

Gate различал режимы:

|Режим|Назначение|
|---|---|
|`explore`|показать gaps без блокировки|
|`dev`|вести агента во время реализации|
|`review`|требовать реализацию и test traces|
|`release`|добавить принятый fingerprint и отсутствие drift|

## Почему это отдельный граф

Сквозной граф только наблюдает связь `AC → CODE → TEST`. Change graph добавляет
управляющее утверждение: «эти узлы составляют текущую работу, а найденные gaps —
её обязательства».

Он ещё может сосуществовать с внешним каноном: требования остаются обычными
Markdown-артефактами, change лишь задаёт scope. Следующая модель делает более
сильный шаг и объявляет stable-ID graph самим контрактом поставки.
