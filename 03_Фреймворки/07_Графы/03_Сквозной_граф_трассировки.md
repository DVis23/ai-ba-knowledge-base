# Сквозной граф трассировки

## Назначение

Сквозной граф отвечает не только «как связаны требования», но и «где они
реализованы и чем проверяются». В одну сеть входят аналитические источники,
спеки, код, тесты и UI.

```text
решение → правило → acceptance criterion → код → тест
                                      └──────→ UI
```

Главный сдвиг относительно БА-графа — появление наблюдаемых технических узлов.
Граф остаётся проекцией файлов. Он расширяет область трассировки, но не владеет
изменением и не создаёт продуктовую истину.

## Слои

|Слой|Примеры узлов|Что утверждает|
|---|---|---|
|Источник|`ST`, `RAC`, решения|Откуда взялся смысл|
|Контракт|`BR`, `AC`, `RULE`, `FLOW`|Какое поведение зафиксировано|
|Реализация|`CODE`, registry declarations|Где находится механизм|
|Проверка|`TEST`, позднее `EVD`|Как контракт проверяется|
|Интерфейс|`UI`, React components, screen zones|Где поведение наблюдает пользователь|
|Навигация|`FILE`|Кто упомянул ID вне артефакта|

Слой не задаёт авторитет автоматически. Код остаётся доказательством текущего
поведения, а не источником требования.

## Устройство

```text
Markdown scanners ───────────────┐
code @trace scanner ─────────────┤
test scanner ────────────────────┼─→ normalized nodes and typed edges
UI sidecars / React scanner ─────┤                │
framework provider facts ────────┘                ▼
                                             SQLite + FTS5
                                                  │
                                     path / impact / coverage / audit
```

### Мета-узлы

Технический мир подключается собственными идентичностями:

- `CODE:<path>` — файл или символ реализации;
- `TEST:<path>` — тестовый файл или тест-кейс;
- `UI:<id>` — UI-sidecar ранней модели;
- `FILE:<path>` — контейнер для ссылки без владельца-артефакта.

Поздние адаптеры добавили более предметные узлы: `CRUDL_RESOURCE`,
`CUSTOM_METHOD`, `ADMIN_PAGE`, `REACT_COMPONENT`, `UI_ZONE`, integration
connections и triggers. Это развитие того же принципа: реализация входит в
граф собственными объектами, а не пересказывается в Markdown.

### Рёбра разной силы

|Класс|Пример|Допустимый вывод|
|---|---|---|
|Навигационный|`MENTIONS`|Файл знает об ID|
|Трассировочный|CODE `IMPLEMENTS` AC|В коде объявлена реализация контракта|
|Тестовый|TEST `COVERS` AC|Тест предназначен для проверки AC|
|Исполнительный|EVD `EXECUTES` TEST|Зафиксирован запуск теста|
|Доказательный|EVD `VERIFIES` AC|Есть допустимое evidence выполнения|
|UI|component `RENDERS` UIC|Компонент отображает зону|

Голое упоминание не становится доказательством. Этот инвариант появился после
опыта с ложной уверенностью: ID в тестовом файле не означает успешный запуск.

### Provider boundary

Framework-specific scanner не должен проникать в универсальное ядро.
Адаптер экспортирует наблюдения в согласованный provider-формат, ядро импортирует
узлы и рёбра без знания Mini, React или другого framework.

```text
Mini registry/runtime
    → mini-graph-ba exporter
    → provider YAML
    → graph-ba import
```

Эта граница появилась в зрелой реализации, но продолжает исходную концепцию
сквозного графа.

## Проверки

|Механизм|Что проверяет|
|---|---|
|`validate <ID>`|ID определён, ссылки разрешаются, обязательные связи есть|
|`coverage`|ожидаемые пары типов связаны|
|`code-refs`|кодовые маркеры доходят до известных артефактов|
|`audit --baseline`|новые структурные дефекты относительно brownfield-снимка|
|auto-import|запрос не выполняется по заведомо пустому или устаревшему индексу|

Эти проверки диагностируют структуру. Они не принимают реализацию за человека.

## Результирующая версия

Семейство началось с CODE-слоя внутри `0.1.0`. Версии `0.2.0–0.2.7` добавили
TEST, UI, React, Mini registry traces, typed metadata и надёжную пересборку.

`0.2.7` — последняя версия, где расширение трассировки было главным
назначением. В `0.2.10` появился собственный lifecycle изменений.
