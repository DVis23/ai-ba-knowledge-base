# Граф БА-документов

## Назначение

Граф БА-документов превращает аналитический корпус в проверяемую сеть. Его
граница — документы: требования, правила, процессы, решения, функции, фичи,
модули и доменная модель.

Граф отвечает:

- где определён ID;
- какие артефакты на него ссылаются;
- выполнено ли ожидаемое межслойное покрытие;
- какие документы затронет изменение;
- где находятся dangling-ссылки, циклы, острова и узкие места.

Он не отвечает, реализовано ли требование, запускался ли тест и готова ли фича.
Эти сущности ещё не входят в модель.

## Источник истины

Источником остаются Markdown-файлы. SQLite-база — пересобираемый индекс. Ручная
правка базы запрещена по архитектуре: следующий import её уничтожит.

Граф не определяет смысл БА-артефакта. Смысл задаёт документный фреймворк:
таксономия, ID-схема, обязательные секции и правила ссылок. graph-ba получает
эту форму через `graph-ba.toml`.

## Устройство

```text
BA Markdown
    │
    ├─ definitions: заголовки и строки таблиц
    ├─ references: ID в тексте
    └─ index tables: связи внутри реестров
             │
             ▼
       directed graph
             │
      ┌──────┴──────┐
      ▼             ▼
 SQLite + FTS5   NetworkX
 поиск/адреса    обходы/audit
```

### Узлы

Первоначальная UpSushi-схема включала:

|Семья|Смысл|
|---|---|
|`ST`|ожидания стейкхолдеров|
|`BR.X`, `BR-XX`|бизнес-требования и правила|
|`BP`, `BD`, `BF`|процессы, решения и функции|
|`F`, `VAD`, `M`|фичи, цепочки ценности и модули|
|`DM`, `SM`, `EN`, `RL`|доменная модель, статусы, справочники и роли|

Узел считается определённым, если найден по правилу `definitions`. ID,
встреченный только как ссылка, становится dangling-узлом. Он сохраняется,
чтобы показать все места, ссылающиеся на отсутствующее определение.

### Рёбра

Ссылка принадлежит ближайшему определению выше по файлу. Упоминание `BR-04`
в секции `BP-02` создаёт направленное ребро `BP-02 → BR-04` с адресом
`файл:строка`.

Первые рёбра выражали в основном структурную связанность. Их семантика
выводилась из типов узлов и coverage-матрицы. Разделение `MENTIONS`,
`IMPLEMENTS` и `VERIFIES` появилось позднее.

### Конфигурация

|Секция|Роль|
|---|---|
|`scan`|корни Markdown-корпуса|
|`types`|regex ссылок и классификация ID|
|`definitions`|места рождения артефактов|
|`index_tables`|связи из табличных реестров|
|`coverage`|ожидаемые пары слоёв|
|`review`|обязательные секции и связи|
|`normalize`|устранение визуально одинаковых ID|

Нормализация была частью корректности. Кириллическая `М` и латинская `M`
иначе создавали два разных узла.

## Рабочий цикл

```text
правка BA-файла
  → import
  → audit/coverage
  → review конкретного ID
  → исправление документа или ссылки
```

Типовые запросы:

|Запрос|Результат|
|---|---|
|`search`|точка входа по ID или тексту|
|`node`|определение и ближайшие соседи|
|`path`|путь между двумя артефактами|
|`impact`|транзитивные зависимости|
|`coverage`|пробелы между слоями|
|`anomalies`/`audit`|структурные дефекты корпуса|

## Инварианты

- Файлы владеют знанием; база владеет только индексом.
- ID стабилен относительно переименования заголовка.
- Каждое ребро имеет адрес происхождения.
- Dangling не скрывается как ошибка парсинга.
- Coverage измеряет связность, а не качество смысла.
- Граф не заменяет человеческий review содержания.
