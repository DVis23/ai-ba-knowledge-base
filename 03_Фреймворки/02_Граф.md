# Граф

Документация — не плоский список файлов, а сеть: артефакты — узлы, ссылки по ID — рёбра. Два термина, которые база строго разводит:

- **Граф** — сама сеть проекта как структура данных с запросами.
- **Граф-инструмент** — движок, который строит эту сеть из файлов и отвечает на запросы. Домен-агностичен: свою схему он получает из конфига конкретного фреймворка ([терминология](../01_Концепция/02_Фреймворк_и_граф.md)).

Глава описывает зрелый граф-инструмент от реальной архитектуры: теория (Часть I), устройство (II), запросы и проверки (III), агентный слой изменений (IV), сборка своего (V).

# Часть I. Теория

## 1. Что решает граф

Задачи, неразрешимые на «куче markdown»:

|Задача|Запрос|Без графа|
|---|---|---|
|**Impact analysis** — что сломается при правке `RULE-01`|`impact RULE-01` — транзитивный обход|ручной grep + надежда|
|**Audit целостности** — висячие ссылки, циклы, сироты, разрывы покрытия|`audit`|текстом не выявить|
|**Coverage** — все ли требования покрыты, все ли спеки трассируются|`coverage`|глазами по сотням файлов|
|**Контекст для LLM** — что подать модели по узлу|срез: узел + типизированные соседи|весь репозиторий или не то|
|**Доказательство реализации** — правило реализовано? проверено тестом?|вычисленные флаги `implemented` / `verified`|вера на слово|
|**Готовность изменения** — можно ли в ревью / релиз|`gate` с режимами|чек-лист в голове|
|**План доказательств** — какие тесты нужны каждому критерию|`evidence-plan`|тест-план вручную|

Первые четыре — классика графа документации. Последние три появляются, когда граф становится сквозным.

## 2. Сквозной граф: документы + код + тесты + UI

Ключевой сдвиг зрелого инструмента: узлы — не только BA-артефакты. Код, тесты и UI-описания не пересказываются в документах — они входят в тот же граф собственными узлами:

|Узел|Откуда берётся|Ребро к артефакту|
|---|---|---|
|`FILE:` — файл-контейнер|документ, где встречена ссылка вне артефакта|упоминание|
|`CODE:` — файл кода|маркер `@trace: RULE-01` в комментарии|код-трасса|
|`TEST:` — тест-файл|любой ID известного типа в тексте теста|тест-доказательство|
|`UI:` — трейс-сайдкар интерфейса|ID в файлах UI-трассировки|UI-трасса|

Цепочка «решение → правило → спека → код → тест» перестаёт быть таблицей трассировки, которую забывают обновлять, — это запрос к графу, пересчитываемый при каждой пересборке.

## 3. Узлы: три сорта

|Сорт|Что это|Зачем в графе|
|---|---|---|
|**Определённый** артефакт|ID рождён по правилу определения (заголовок, строка таблицы, явный блок)|основное содержание|
|**Dangling** — висячий|ID упомянут, но нигде не определён|улика для `audit`: сослались на несуществующее|
|**Мета-узел**|`FILE:` / `CODE:` / `TEST:` / `UI:`|пришивает не-markdown-мир к графу|

Dangling — тоже узел, а не ошибка парсинга: на него указывают рёбра, по ним видно всех виновных. Если `BP-01` не определён, но есть варианты `BP-01a`, `BP-01b` — ссылки переносятся на варианты автоматически.

## 4. Рёбра: типизированные, адресуемые, слабые и сильные

Каждое ребро несёт **тип связи** и **адрес происхождения** (файл:строка). Повторные упоминания в разных местах — отдельные рёбра: видно каждое место, где артефакты связаны.

Словарь типов мал и фиксирован (~16 значений), по силе делится на три группы:

|Группа|Типы|Роль|
|---|---|---|
|**Слабые**|упоминание (`MENTIONS`), связь из индекс-таблицы|навигация; в доказательства не идут|
|**Трассировочные**|код-трасса, тест-доказательство, UI-трасса|пришивают реализацию и проверки|
|**Семантические**|`IMPLEMENTS`, `DEPENDS_ON`, `VERIFIES`, `RENDERS`, `CONTAINS`, `TRACES_TO`, `NORMALIZES`, `SUPERSEDES`, `CONFLICTS_WITH`, `TRACE_GAP`|осмысленные утверждения о связи|

Два правила дисциплины:

- **Не изобретай новые слова-связи.** Политика проекта описывается разреженной матрицей «тип источника × тип цели × связь» на общем словаре, а не новым словом на каждый случай. Иначе словарь распухает и агент перестаёт понимать семантику.
- **Слабое — не доказательство.** Текстовое упоминание правила в файле кода не значит «реализовано». Доказательства строятся только по трассировочным и семантическим рёбрам; упоминания исключаются из агентских срезов по умолчанию.

## 5. Происхождение узла (origin)

Второе измерение метаданных, ортогональное типу узла: **кто породил знание**.

|Origin|Значение|Пример|
|---|---|---|
|`human`|первоисточник от человека|рафинат встречи|
|`canonical`|согласованная истина|принятое правило, спека|
|`derived`|производный артефакт|индекс, агрегатор|
|`evidence`|доказательство|тест, UI-трасса|
|`implementation`|реализация|файл кода|
|`container`|контейнер|`FILE:`-узел|

Это машинная форма иерархии источников истины из [спек](04_Спеки.md): чем можно обосновывать факт. Модель, получив срез графа, видит не только «узлы связаны», но и «этот узел — канон, этот — производный индекс, числа брать из первого».

## 6. Ручной минимум, вычисляемое состояние

Принцип: **руками проставляется только жизненный цикл** (`draft / planned / accepted / archived`). Всё остальное состояние выводится из фактов графа:

|Флаг|Как вычисляется|
|---|---|
|`implemented`|существует путь от узла реализации по сильным рёбрам|
|`verified`|есть тест-доказательство или `VERIFIES` от evidence-узла|
|`changing`|артефакт в scope активного изменения (Часть IV)|
|`stale`|текущий отпечаток разошёлся с принятым снимком|

Отпечаток артефакта — хэш по четырём измерениям: содержание, связи, наблюдаемое, доказательства. Сравнение снимков отпечатков даёт `stale` — документный аналог drift-checks [кодовой семьи](06_Код_фреймворк.md): «декларация разошлась с реальностью» ловится машинно, а не на ревью.

## 7. Инварианты хорошего графа

|Инвариант|Что ломается без него|
|---|---|
|**Одна семантика узла** — узлы суть артефакты, мета-узлы помечены|запросы возвращают микс|
|**Типизированные направленные рёбра**|«связано» без смысла, impact врёт|
|**Стабильные ID**|переименование = граф рассыпался|
|**Источник — файлы, граф генерируется**|правленный руками граф мёртв назавтра|
|**Идемпотентная пересборка** — импорт без изменений = no-op|каждая пересборка «шумит»|
|**Авто-пересборка перед запросом**|запрос по устаревшему графу тихо врёт|
|**Версия схемы БД** — несовпадение = автоматический rebuild|старый кэш маскируется под данные|
|**Малый словарь связей**|семантику рёбер никто не помнит|
|**Запросы, а не картинка**|диаграмма на 600 узлов нечитаема|

# Часть II. Устройство инструмента

## 8. Архитектура

```
markdown  код  тесты  UI-сайдкары  изменения (change.yaml)
   └───────┴────┴───────┴──────────────┘
             сканеры (regex по конфигу)
                      │
                SQLite + FTS5          ← персистентный индекс
                      │
             граф в памяти (обходы)    ← impact / audit / gate
                      │
        CLI (--json, exit-коды)  +  MCP-сервер
```

Реализация компактна: Python, stdlib `sqlite3`, библиотека графов для обходов, CLI-библиотека — порядка 10 тыс. строк вместе с агентным слоем. Хранилище персистентно (файл БД в каталоге отчётов), обходы — в памяти при каждом запросе.

## 9. Конфиг — декларативное описание домена

Один TOML-файл в корне проекта. Инструмент не навязывает конвенций: типы, ID-паттерны и правила — целиком из конфига.

|Секция|Что задаёт|
|---|---|
|`scan`|каталоги для скана markdown|
|`types.<T>`|тип артефакта: `ref`-regex поиска ссылок, origin, `restrict_to` (сузить область действия паттерна)|
|`definitions`|где артефакт **рождается**: `mode="heading"` или `"table"` + regex (ID, заголовок)|
|`index_tables`|таблицы-индексы: ID первой колонки → рёбра ко всем ID строки|
|`coverage`|ожидаемое межслойное покрытие: `source="FEATURE", target="RULE"`|
|`review`|обязательные секции по типу, ожидаемые межслойные и двусторонние связи|
|`clusters`|семантические группы узлов (тема → список ID)|
|`code` / `tests` / `ui`|каталоги, расширения, маркер `@trace`; для тестов и UI маркер не нужен — любой ID известного типа|
|`lint`|глоссарий, каталог встреч, порог свежести, TODO-паттерны|
|`normalize`|замены символов (кириллическая `М` → латинская `M`), zero-padding (`REQ-1` → `REQ-01`)|
|`range_pattern`|развёртка диапазонов `BR.12.1–BR.12.6` в отдельные ID|
|`origins` / `relations`|переопределение словарей происхождения и связей (обычно не нужно)|
|`graph_native`|каталог изменений и явных блоков-артефактов (Часть IV)|

Regex с lookbehind/lookahead `(?<![A-Za-z.])(RULE-\d{2})(?!\d)` отличает `RULE-01` от `RULE-011` и `XRULE-01`. Нормализация ID обязательна в русскоязычном корпусе: кириллическая буква в ID, набранная «на глаз», иначе порождает узел-двойник.

## 10. Сканирование: как текст становится графом

1. **Определения.** По правилам `definitions`: заголовок `# RULE-01 …`, строка таблицы, либо явный типизированный блок-артефакт. Первое определение выигрывает; ID нормализуется.
2. **Ссылки.** По `ref`-regex всех типов, вне код-блоков. Каждая ссылка — с файлом, строкой и текущей секцией.
3. **Владелец ссылки.** Ссылка приписывается ближайшему определению **выше по файлу** — так упоминание `RULE-01` внутри секции `PROC-02` даёт ребро `PROC-02 → RULE-01`. Нет определений в файле — владелец `FILE:`-узел.
4. **Dangling и варианты.** Неопределённые ID становятся dangling-узлами; при наличии вариантов (`BP-01` → `BP-01a/b`) рёбра переносятся на варианты.
5. **Код, тесты, UI.** Сканы исходников по `@trace`-маркеру, тест-файлов и UI-сайдкаров по голым ID — мета-узлы и трассировочные рёбра.
6. **Индекс-таблицы и изменения.** Рёбра из индексов; scope активных изменений — рёбра от узла изменения.
7. **Запись.** Таблицы БД пересобираются целиком, снимок mtime файлов сохраняется.

## 11. Хранилище

|Таблица|Содержание|
|---|---|
|`artifacts`|`id, type, origin, title, source_file, line_number, defined`|
|`edges`|`source_id, target_id, relation_type, context, source_file, line_number`; составной PK — мульти-рёбра различимы по месту|
|`artifact_origins`, `relation_types`|словари происхождения и связей — самоописание графа|
|`semantic_clusters`|кластеры из конфига|
|`scanned_files`, `meta`|mtime-снимок и время импорта — для детекции устаревания|
|FTS5-индексы|полнотекст по артефактам, контекстам рёбер, кластерам|

Граф — проекция файлов, не источник: руками не правится, любая правка — в markdown и пересборка.

## 12. Надёжность для агента

Свойства, ради которых инструмент можно отдать LLM без няньки:

- **Auto-import guard.** Перед любым read-запросом: граф пуст или устарел (mtime файлов изменился) — пересборка автоматически. Тихий пустой результат на неимпортированном графе — худший отказ для агентских сценариев: модель примет «ничего не найдено» за факт.
- **Версия схемы.** Несовпадение версии БД — автоматический drop и rebuild, старый кэш не маскируется под данные.
- **`--json` на всех командах** — машинный вывод без парсинга текста.
- **Детерминированные exit-коды** (`lint`, `validate`, `gate`, `audit --baseline`) — команды встают в CI и агентские циклы как есть.
- **MCP-сервер.** Те же запросы (поиск, узел, impact, coverage, audit, ревью, схема графа) — инструментами MCP; произвольный SQL — строго read-only. Модель работает с графом без shell-доступа.

# Часть III. Запросы и проверки

## 13. Навигация

|Команда|Что делает|
|---|---|
|`search <текст>`|FTS5-полнотекст по артефактам, рёбрам, кластерам — точка входа|
|`node <ID>`|узел + входящие/исходящие соседи; при промахе — похожие ID|
|`path <A> <B>`|кратчайший путь (сначала направленный, затем без направления)|
|`impact <ID>`|транзитивно: потомки (что заденет правка) + предки (контекст), сгруппированы по типу|
|`review <ID> --semantic`|полный контекст артефакта: связи, проблемы, **текст связанных артефактов**|

Связка «FTS находит точку входа → обход достраивает контекст по связям» надёжнее embedding-поиска в одиночку: релевантность задана структурой, а не похожестью текста.

`review` дополнительно ловит **числовые конфликты**: одна величина (проценты, деньги, время) в артефакте и его соседях с разными значениями — кандидат на расхождение single source of truth.

## 14. Контроль качества

**`lint`** — качество содержания:

|Проверка|Ловит|
|---|---|
|TODO-маркеры|незавершённость (`TODO/TBD/FIXME/???`) в секции артефакта|
|Пустые секции|заголовок есть, содержания нет|
|Терминология|неканоничные термины по глоссарию проекта|
|Свежесть|файл не менялся дольше порога с последней встречи|
|Покрытие кодом|артефакты заявленных типов без единой код-трассы|

**`validate <ID>`** — детерминированный gate одного артефакта: определён, исходящие ссылки резолвятся, обязательные секции на месте, ожидаемые межслойные связи есть. Провал — ненулевой exit-код: ставится в конвейер скиллов («lint после правки») и в CI.

**`coverage`** — матрица ожидаемых связей из конфига: покрытие в процентах + отдельные блоки покрытия кодом/тестами/UI.

**`audit`** — структурные проблемы всего графа: циклы, dangling, острова, мосты (критические одиночные связи), узлы-бутылочные-горлышки, разрывы покрытия, отсутствие ожидаемой двусторонности. Выход — приоритизированный список кандидатов на ревью.

**Baseline-ratchet** — ключ к brownfield. На живом корпусе сотни легаси-проблем; аудит, который всегда красный, перестают читать. Каждая проблема получает стабильный отпечаток; `--write-baseline` фиксирует известные, дальше `audit --baseline` падает **только на новых**. Храповик: хуже становиться нельзя, лучше — можно.

## 15. Отчёты и экспорт

|Что|Зачем|
|---|---|
|`matrix`|разреженная матрица «тип × тип × связь» с уликами (файл:строка) — политика связей проекта как данные|
|`pack <ID>`|markdown-бандл: тексты артефактов + типизированные связи — передать человеку или модели одним файлом|
|экспорт JSON / DOT / HTML|обмен, Graphviz, автономная интерактивная визуализация с фильтрами|
|индекс артефактов|компактный `ARTIFACT_INDEX.md` для навигации агента без запросов|

Визуализация — вспомогательный экспорт, не ценность: работа идёт через запросы.

# Часть IV. Граф-нативные изменения: агентный слой

Слой поверх графа, превращающий его из индекса в **рабочую поверхность изменений**. Идея та же, что у дельт [OpenSpec](04_Спеки.md) (Propose → Review → Apply → Archive), но единица — не спека, а произвольный scope узлов графа.

## 16. Изменение как артефакт

Изменение живёт в каталоге `changes/<id>/` файлом `change.yaml`: заголовок, состояние (`draft/planned/accepted/archived`), режим, **scope** — список затрагиваемых ID. При импорте изменение само становится узлом графа с рёбрами на свой scope.

Workflow: `create → compile → check → accept → archive`. `compile` генерирует срез, worklist, план доказательств и человекочитаемые отчёты; `accept` фиксирует принятый снимок отпечатков (от него считается `stale`); `archive` уводит в архив с датой.

## 17. Gate: готовность по режимам

`gate <ID>` оценивает scope и отвечает «можно ли дальше» с ненулевым exit-кодом на провале:

|Режим|Требует|
|---|---|
|`explore`|ничего не блокирует — черновая работа|
|`dev`|предупреждения видимы, работа не блокируется|
|`review`|контрактные типы реализованы, критерии приёмки покрыты тест-доказательствами|
|`release`|плюс принятый снимок и отсутствие `stale`|

Выход структурирован: оси качества (трассируемость, доказательство реализации, тест-доказательства, дрифт), находки с типом пробела (`GAP-AC`, `GAP-TEST`, `GAP-DRIFT`, …) и предлагаемым исправлением. Один и тот же gate держит и агента в цикле, и CI.

## 18. Срез графа и worklist

`graph <ID>` — версионированный JSON-срез для модели:

- **узлы scope** с вычисленными флагами (`implemented/verified/changing/stale`) и выдержками содержания;
- **типизированные рёбра** — слабые упоминания исключены;
- **каталог связей** — значения словаря прямо в срезе, агент не хардкодит семантику;
- **worklist** — детерминированный список «что чинить дальше» с приоритетами P0–P2.

Это ответ на вопрос «какой контекст дать модели»: не репозиторий и не файл, а срез + план работ, посчитанные из графа.

## 19. Evidence-plan: какие доказательства нужны

`evidence-plan <ID>` классифицирует каждый критерий приёмки в scope (по типам связанных узлов и ключевым словам) и выводит **требуемые виды доказательств**: алгоритм — unit-тест, поведение бэкенда — интеграционный, видимое в UI — e2e, контракт — контракт-тест. Сравнивает с наблюдаемыми тест-доказательствами в графе — остаток и есть тест-план. Политика соответствия расширяется файлом проекта.

## 20. Skills поверх графа

Инструмент несёт собственные скиллы — процедуры для LLM-среды: переиндексация, семантический ревью артефакта, impact перед правкой, **аудит-воронка** (структурный `audit` отбирает подозрительных → параллельные субагенты делают семантический ревью каждого). Граф отвечает «где смотреть», модель — «что там не так»: машинная структура + семантика LLM, каждый делает своё.

# Часть V. Собрать или адаптировать

Минимальный виток — день работы, дальше слои наращиваются по мере боли:

1. **Ядро.** Перечисли типы и ID-форматы → `types` + `definitions`; задай ожидаемые связи → `coverage`. Парсер + SQLite + `import / node / impact / lint`. Уже полезно: dangling и impact работают.
2. **Качество.** `review`-правила (обязательные секции, межслойные связи), `audit` + baseline-ratchet, глоссарий для терминологии.
3. **Сквозные слои.** `@trace`-маркер в коде, скан тестов и UI — граф становится сквозным, появляются `implemented/verified`.
4. **Агентный слой.** Изменения со scope, gate по режимам, срезы и worklist — когда над графом начинают работать агенты, а не только люди.

Правила переноса: код инструмента домен-агностичен — адаптация это конфиг; словарь связей не расширяй без нужды; каждое правило проверки — с автопроверкой и exit-кодом, иначе оно живёт только в голове.

## Definition of done

- [ ] Граф пересобирается из файлов одной командой; руками не правится.
- [ ] Запрос по устаревшему/пустому графу невозможен (авто-пересборка).
- [ ] ID нормализуются; dangling видимы в audit, а не теряются.
- [ ] Слабые упоминания отделены от трассировочных и семантических рёбер.
- [ ] `lint`/`validate`/`gate` дают детерминированные exit-коды и стоят в CI.
- [ ] На brownfield-корпусе audit работает через baseline-ratchet.
- [ ] Для модели есть машинный доступ: `--json` и/или MCP.
