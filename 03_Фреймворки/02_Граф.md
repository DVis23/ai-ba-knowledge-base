# Граф

Документация — не плоский список файлов, а сеть. Любая ссылка по ID (`RULE-01 → PROC-02 → DEC-02`) — ребро, любой артефакт — узел. На сотнях артефактов и тысячах связей выбор простой: либо граф, либо потеря контроля.

Этот документ — как **построить свой граф-инструмент**: архитектура из четырёх частей, по которой читатель соберёт аналог под любой домен.

## Что решает граф

Четыре задачи, неразрешимые на «куче markdown»:

|Задача|Запрос|Без графа|
|---|---|---|
|**Impact analysis** — что сломается при правке `RULE-01`|`impact RULE-01` (обход вниз)|ручной grep + надежда|
|**Audit целостности** — висячие ссылки, циклы, сироты|`audit`|текстом не выявить|
|**Coverage** — все ли требования покрыты, все ли спеки трассируются|`coverage`|глазами по сотням файлов|
|**Контекст для LLM** — что подать модели по узлу|узел + соседи|весь репозиторий или не то|

## Архитектура: четыре части

```
markdown/*.md ──parser(regex по конфигу)──▶ SQLite ──queries──▶ impact / lint / coverage
       ▲                                                                  │
       └──────────────── правки артефактов ◀── отчёт ─────────────────────┘
```

Реализуется как небольшой CLI (Python + стандартный `sqlite3` достаточно). Дальше — что в каждой части.

### 1. Конфиг — декларативное описание домена

Файл (TOML/YAML) задаёт: какие бывают типы артефактов, как их найти в тексте, какие связи ждать. Минимальный набор секций:

|Секция|Что задаёт|Пример|
|---|---|---|
|`scan`|где искать|`dirs = ["requirements", "specs"]`|
|`types.<T>`|тип + regex поиска ссылок|`ref = '(?<![A-Za-z.])(RULE-\d{2})(?!\d)'`|
|`definitions`|где артефакт **определяется** (не просто упомянут)|`mode="heading"`, `pattern='^#\s+(RULE-\d{2})'`|
|`coverage`|ожидаемые связи|`source="FEATURE", target="RULE"`|
|`lint`|пороги|`stale_threshold_days=30`, `todo_patterns=["TODO","TBD"]`|

Regex с negative lookbehind/lookahead `(?<![A-Za-z.])(RULE-\d{2})(?!\d)` отличает `RULE-01` от `RULE-011` и от `XRULE-01` — без этого ID путаются. Конфиг — то, что адаптируешь под свой домен; остальной код переиспользуется.

### 2. Парсер — markdown → узлы и рёбра

Конвейер на каждом файле:

1. **Найти определения.** По `definitions` (режим `heading`/`table`/`text`) — где артефакт **рождается** (заголовок `# RULE-01 …`, строка таблицы). Это узел: `(id, type, title, source_file, defined=true)`.
2. **Найти ссылки.** По `ref`-regex всех типов — где артефакт **упоминается**, с контекстом ±символы: `(artifact_id, file, line, context)`.
3. **Резолвить.** ID → файл по glob-правилам типа. Нет определения → **dangling** (висячая ссылка).
4. **Детектить drift.** Контекст вокруг `RULE-02` не пересекается с реальным заголовком `RULE-02` → кандидат на рассинхрон (сослались не на то).
5. **Построить рёбра.** Упоминание `RULE-01` внутри `PROC-02` → ребро `(PROC-02 → RULE-01, type=cites, location)`.

### 3. Хранилище — SQLite

|Таблица|Поля|
|---|---|
|`nodes`|`id, type, title, source_file, defined`|
|`edges`|`source_id, target_id, type, file_location`|
|`references`|`artifact_id, file, line, context`|

Машинно-генерируемое: `import` пересобирает БД из markdown целиком. Граф **не правится руками** — иначе разойдётся с реальностью назавтра. Источник истины — артефакты, граф — их проекция. Для текстового поиска добавь SQLite FTS5-индекс по заголовкам и телам.

### 4. Запросы

|Команда|Что делает|Как реализовать|
|---|---|---|
|`import`|пересобрать БД из markdown|парсер из части 2|
|`lint [<ID>]`|TODO/TBD, висячие ID, циклы, свежесть|обход + проверки по `lint`-конфигу|
|`audit`|двусторонность ссылок, coverage-разрывы, аномалии|сверка с `coverage`-правилами|
|`impact <ID>`|потомки (что зависит) + предки (контекст), с глубиной|BFS по `edges` вниз и вверх|
|`coverage`|матрица покрытия|проекция рёбер на `coverage`-правила|
|`node <ID>`|узел + соседи + `файл:строка`|выборка + 1–2 уровня связей|
|`path <A> <B>`|кратчайший путь|BFS между узлами|

`impact RULE-01` вернёт потомков (`PROC-02`, `RULE-09`, `FEATURE-04`) и предков (`DEC-02`, `PROC-02`) — сразу видно, что протухло при правке.

## Что граф даёт именно LLM

Для людей граф — про картинки, для LLM — про контекст:

- **Подграф как контекст.** `node RULE-01` → узел + соседи с `файл:строка`. Модель грузит это, не весь репозиторий.
- **Стабильные адреса.** Не пересчитывает «о чём файл» — есть ID и связи.
- **Валидация генерации.** ИИ сослался на `RULE-99` — граф ловит: такого узла нет.
- **FTS + обход.** Полнотекст находит точку входа, обход графа достраивает контекст по связям — лучше любого embedding-поиска в одиночку.

## Хороший граф против никакого

|Свойство|Зачем|
|---|---|
|**Одна семантика узла**|все узлы — артефакты, не микс|
|**Типизированные рёбра**|`cites/implements/triggers`, а не «связано»|
|**Направленность**|`требование → реализация` ≠ наоборот|
|**Стабильные ID**|переименование = новый узел = граф рассыпался|
|**Источник — артефакты**|граф генерируется, не рисуется руками|
|**Машинная пересборка**|`import` из markdown, иначе мёртв через неделю|
|**Запросы, а не картинка**|ценность в `impact/coverage`; картинка на 600 узлов нечитаема|

## Как собрать под свой домен

1. Перечисли типы артефактов и их ID-формат → секция `types` с regex.
2. Опиши, где артефакт **рождается** (заголовок/таблица) → `definitions`.
3. Задай ожидаемые связи → `coverage`.
4. Напиши парсер (5 шагов выше) и сложи в SQLite.
5. Реализуй запросы поверх `edges` (BFS для impact/path).

Код парсера и запросов домен-независим — меняется только конфиг. Связь с триадой и БА → [Триада](01_Триада.md), [БА-фреймворк](03_БА_фреймворк.md).
