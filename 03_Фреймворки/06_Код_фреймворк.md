# Код-фреймворк

Документные фреймворки (БА, спеки) переиспользуешь как есть — markdown + ID + граф домен-агностичны. **Код-фреймворк привязан к стеку**: связка веб-фреймворк + ORM + хранилище у каждого своя, готовый под твой стек редко подходит. Собрать его — замыкающая компетенция фулл-стек ИИ-специалиста.

Приём тот же: **зафиксируй форму, освободи содержание, проверь автоматически.** Материал другой — форма исполняемая (декларации + кодогенерация), проверки — типы, снимки схемы, архитектурный линтер, тесты. Глава описывает зрелый код-фреймворк от реальной архитектуры (Python: FastAPI + PostgreSQL + SQLAlchemy, админка на React): философия (Часть I), декларативное ядро (II), платформенные подсистемы (III), экосистема расширений (IV), само-верификация (V), агентная обвязка (VI), сборка своего (VII).

# Часть I. Философия

## 1. Агент — основной пользователь

Классические фреймворки (Rails, Django) — human-first: DRY-магия, конвенции в голове, «умные» базовые классы. Код-фреймворк для ИИ проектируется **agent-first** — на уровень абстракции выше классических, — и из этого следует всё остальное:

|Следствие|Почему|
|---|---|
|Маленькое ядро|проект должен влезать в контекст модели|
|Архитектура решена заранее|агент не проектирует её, а выбирает способ реализации из готовых|
|Каждое архитектурное решение = ADR + правило линтера|решение без автопроверки агент нарушит на втором прогоне|
|Декларации вместо boilerplate|~80% объёма типовой бизнес-системы — обвязка (CRUD, права, миграции, админка, аудит, jobs, интеграции); она генерится детерминированно|
|CLI-карта проекта|агент спрашивает «что где», а не читает репозиторий|
|Скиллы и хуки в комплекте|фреймворк приносит процедуры и проверки в среду агента сам|

Это ответ на «вайбкодинг»: без рельс LLM генерирует правдоподобный код, архитектура складывается случайно и расходится при первом изменении. Тезис фреймворка: **агент полезнее, когда рассуждает о поведении продукта, а не регенерирует обвязку.**

Стек при этом обычный (веб-фреймворк, реляционная БД, React) — проект передаётся заказчику вместе с фреймворком, без lock-in на экзотику.

## 2. Лестница путей данных

Один водораздел определяет всё: **«сохрани строку» против «сделай что-то»**. На практике он разворачивается в лестницу — каждый следующий путь берётся, только если предыдущий не выражает задачу:

|Путь|Когда|Кто пишет|
|---|---|---|
|**CRUDL** — list / get / create / update / delete|типовые данные|генерится из декларации|
|**Агрегат** — счётчики, суммы, группировки|отчётность, дашборды|генерится (§10)|
|**Кастомный метод** — именованная операция с контрактом|действие, которое CRUD не выражает: чекаут, пересчёт, bulk|ИИ — handler; контракт — декларация (§8)|
|**Сырой роут**|вебхуки, файлы, стриминг, чужие протоколы|ИИ, с явной пометкой «сырой»|

Отдельная дисциплина — **классификация границы интеграции**: прежде чем писать код, трогающий внешнюю систему, агент обязан заявить класс границы (сервис / кастомный метод / job / durable-workflow / коннектор) и обоснование. Правило операционного контракта; нарушение ловится на ревью и линтером.

## 3. Словарь ядра

Шесть понятий, каждое с одной ролью:

|Понятие|Роль|Не делает|
|---|---|---|
|**Resource**|декларация формы данных: поля, связи, политики|поведения|
|**CRUDL + агрегат**|генерируемые чтение/запись с правами, фильтрами, пагинацией|доменных решений|
|**CustomMethod**|вызываемый не-CRUD контракт: код, endpoint, право, идемпотентность|транспортных деталей в handler'е|
|**Service**|инварианты, расчёты, мультизапись — владение расширения|транспорта|
|**Route handler**|тонкий адаптер HTTP|бизнес-решений|
|**Workflow**|durable-граница внешних систем: retry, replay, evidence|внутренней логики|

## 4. Дефолтная архитектура: модульный монолит с синхронным ядром

Один рантайм, синхронная реляционная БД, расширения-модули, прямые in-process вызовы, опциональная изоляция тенантов схемами БД. Границы модулей достаточно явные, чтобы позже выделить сервис — но не раньше, чем это понадобится.

Три правила, которые чаще всего спасают агента от самострела:

- **Синхронное ядро.** `async` — только там, где тело действительно ждёт ввода-вывода; синхронная работа с БД в async-контексте уходит в thread pool. Асинхронный ORM запрещён линтером: две модели конкурентности в одном ядре — источник трудноуловимых багов.
- **Транзакция не живёт поверх внешнего вызова.** HTTP к чужому API внутри открытой транзакции — находка линтера.
- **Сервисы зовут рантайм напрямую, не свой REST.** Внутри процесса нет HTTP к самому себе.

# Часть II. Декларативное ядро

## 5. Дескриптор: Resource + Field

Ресурс описывается **данными, не кодом** — иммутабельные структуры:

```python
resource = Resource(
    name="orders", title="Заказы", table_name="orders",
    fields=(
        field.id(),
        field.public_id(),                        # server-default UUID
        field.string("number", required=True, unique=True, list=True),
        field.money("total"),                     # целые копейки + семантика единицы
        field.status("status"),
        field.datetime("created_at", server_default="now"),
    ),
    permissions={"read": "orders.read", "write": "orders.write", "delete": "orders.delete"},
    relations=(Relation("customer_id", "customers", display_field="name",
                        on_delete="restrict"),),
    state_machine=StateMachinePolicy(
        field="status", initial="new",
        transitions=(StateTransition("pay", from_states=("new",), to_state="paid",
                                     permission="orders.write", audit_event="order.paid"),),
    ),
    audit=AuditPolicy(enabled=True),
    idempotency=IdempotencyPolicy(actions=("create",)),
)
```

Помимо полей и политик декларация несёт: связи (с правилом `on_delete` и полем отображения — includes строятся только по объявленным связям, это не произвольный query-движок), индексы (включая partial / covering / GIN), уникальности и check-ограничения, **профиль хранения** (`config` / `audit` / `ledger` / `queue` — профиль сам подстраивает точность count'ов и включает курсорную пагинацию для append-only данных), поверхности API и права.

Декларация — единственный источник правды о контракте ресурса. Историю БД держат миграции, не она.

## 6. Поля: типы, источники, семантика

Поле объявляется фабрикой (`field.string(...)`, `field.money(...)`) и несёт больше, чем колонка:

|Измерение|Что задаёт|
|---|---|
|**Тип**|скаляры (int/bigint/decimal/uuid/date/datetime/json), медиа (image/video/file + множественные, с политикой обработки: формат, ресайз, чистка метаданных), векторы (размерность, метрика), гео (точка/линия/полигон)|
|**Хранение и валидация**|required / readonly / nullable, default и server-default, длина, точность, min/max, regex-паттерн|
|**Видимость по слоям**|`api` / `list` / `form` / `filter` / `sort` + допустимые операторы фильтра; admin-переопределения отдельно|
|**Источник**|`manual` — пишет пользователь; `derived` — вычисляемое, с указанием из чего и **кем поддерживается** (БД / сервис / проектор / backfill); `external` — чужое, readonly|
|**Семантика единицы**|смысл числа: деньги в копейках, проценты, количество. Объявлена явно, но намеренно **не** влияет ни на тип колонки, ни на хэши контракта|
|**Схемы UI**|JSON Schema + нейтральные UI-подсказки для генерации форм|

Разделение «источник поля» отвечает на вопрос, который агент иначе решает случайно: кто имеет право это поле менять. Разделение «семантика ≠ хранение» позволяет уточнять смысл без ложных срабатываний дрифта.

## 7. Политики: поведение данными

Всё сквозное поведение — декларации на ресурсе, а не код в эндпоинтах. Добавил политику — поведение появилось у всех операций ресурса:

|Политика|Задаёт|
|---|---|
|`CachePolicy` / `HttpCachePolicy`|кэш с TTL и инвалидацией по событиям; ETag считается от версии кэша + отпечатка запроса, не от строк|
|`AuditPolicy`|журнал: события, snapshot до/после, какие поля скрыть, ретеншн|
|`IdempotencyPolicy`|ключ в заголовке, действия, TTL, обязательность|
|`RowScopePolicy`|видимость строк по полю актора; наследование по объявленной связи; right-to-bypass отдельным правом|
|`StateMachinePolicy`|FSM: состояния, переходы с правами, аудит-событиями и side-полями; трекинг (когда сменился, история, длительность)|
|`VersioningPolicy`|draft → publish → archive, ревизии, предпросмотр, отложенная публикация|
|`QueryPolicy` / `SearchPolicy`|фильтр-AST с лимитами глубины и числа условий; поиск: prefix / contains / trigram / fulltext|
|`ImportExportPolicy`|поля, формат, upsert-ключ, размер батча|
|`ExternalSyncPolicy`|поля соответствия внешней системе: external id, статус, время синка, payload|
|`ProjectionPolicy`|материализованные проекции: вручную / по событию / по расписанию|
|`LocalizationPolicy`|локали и стратегия (строкой или полем)|
|`ObservabilityPolicy`|метрики/трейсы с low-cardinality метками|
|`ApiContract`|версия, стабильность, deprecation, алиасы полей|

Частые связки собраны в **композитные фабрики**: одна декларация «черновик-публикация» разворачивается в статусные поля + FSM + версионирование + аудит + идемпотентность. Собранное руками из тех же кирпичей — эквивалентно; фабрика фиксирует проверенную комбинацию.

## 8. Кастомный метод — контракт операции

«Сделай что-то» тоже оформляется декларацией; свободен только handler:

|Поле контракта|Зачем|
|---|---|
|`code`, `endpoint`, HTTP-метод|стабильный адрес операции|
|`kind`: query / command / aggregate|чтение или изменение — для кэша и семантики|
|`permission`|право, без него метод не смонтируется|
|`idempotent`, `invalidates`|повторный вызов безопасен; какие кэши сбросить|
|request/response-схемы|JSON Schema или модели валидации → OpenAPI и формы админки|
|`surfaces`: admin / client / integration / internal|на каких API метод виден|
|`api_version`, `stability`, `deprecation`|эволюция: ломающее изменение = новый `code` (`*.v2`), не тихая правка|

Валидатор на старте проверяет: право существует, `invalidates` ссылается на живые ресурсы, маршрут уникален. Метод с admin-поверхностью автоматически появляется в админке — с формой, сгенерированной из request-схемы.

## 9. Генерация: что рождается из декларации

```
Resource + Field + CustomMethod
        │
        ├─▶ таблица БД (метаданные ORM, индексы, ограничения, расширения БД под гео/векторы)
        ├─▶ модели валидации create / update / read → OpenAPI
        ├─▶ REST: GET/POST/PATCH/DELETE /{name}, GET /{name}:meta,
        │        GET /{name}:aggregate, :export / :import,
        │        GET /{name}:transitions, POST /{name}/{id}:transition
        ├─▶ admin-манифест: навигация, экраны, формы, действия (§15)
        ├─▶ клиентский контракт: JSON + contract_hash → кодоген SDK (§20)
        └─▶ снимок схемы + черновик миграции (§23–24)
```

**Сгенерированное руками не правят** — бизнес-код туда не попадает.

## 10. Агрегаты — третий вид чтения

Рядом со списком и карточкой: счётчики, суммы, средние, min/max, медианы и перцентили, `group_by` с временными бакетами (час…год, с явной таймзоной), фильтрованные меры, top-N, HAVING. Тем же языком фильтров, с теми же правами, row-scope и кэшом, что у списка.

Смысл в дисциплине, а не в SQL: агрегат в сервисе руками (`select(func.sum(...))`) — находка линтера. Дашборды и отчёты перестают быть источником самописных запросов, расползающихся мимо прав и кэша.

## 11. Рантайм: public and boring

Один движок исполняет все ресурсы, применяя политики из деклараций. Для сервисов — **публичный скучный API**: карта ресурсов → обёртка ресурса → fluent-запрос (`where / search / include / sort / page`) + операции с контекстом (сессия, актор, поверхность). Скучный — сознательно: у API для агента не должно быть двух способов сделать одно и то же.

## 12. Escape hatch: слои

Что CRUD не выражает — пишется явно, по слоям с жёсткими ролями (роутер / сервис / рантайм / адаптер — §3). Правило: не схлопывать бизнес-логику ни в роутер, ни в генерёжку. «AI-native» — это *код удобно инспектировать и проверять*, а не «логика спрятана за DSL»: утопил смысл в декларациях — сломал фреймворк.

# Часть III. Платформенные подсистемы

Подсистемы, которые в проекте без фреймворка пишутся заново и каждый раз чуть по-другому. Здесь они framework-owned и декларативны.

## 13. Jobs и ретеншн

Фоновая задача — декларация: код, handler, расписание, батч. Воркер, журнал запусков и admin-видимость — у фреймворка. Встроенный системный job ретеншна чистит по расписанию техданные (ключи идемпотентности, журналы запусков, аудит по истечении срока) — гигиена, о которой проект обычно вспоминает после инцидента.

## 14. Интеграции и workflows: durable-границы

Внешняя система — это отказ, ретрай и вопрос «что мы ей уже отправили». Граница оформляется декларациями трёх видов: **connection** (куда и как подключаемся), **action** (что вызываем), **trigger** (на что реагируем). Исполнение durable: журнал запусков, ретраи с политикой, replay, доказательства вызова (evidence), circuit breaker, видимость в админке.

Правило, подкреплённое баном линтера: **исходящий HTTP живёт только внутри интеграционной границы** — «просто вызову API из сервиса» не проходит. Стандартные коннекторы (HTTP, объектное хранилище) — в ядре, остальное — пакетами (§19).

## 15. Админка: backend-driven UI

Админка — не рукописное приложение, а **оболочка, которую ведёт реестр**: навигация, список/карточка/форма, фильтры, действия и переходы FSM приходят манифестом с бэкенда. Декларация admin-метаданных на ресурсе задаёт группу, иконку, колонки, действия в слотах экрана, предпросмотр; формы генерятся из тех же схем валидации (рендерер — по JSON Schema).

Кастомные экраны легальны для четырёх случаев: конструкторы, композеры, мониторы, дашборды. Всё остальное — генерируемые экраны; рукописный CRUD-экран — smell. Манифест несёт версию схемы и хэши контрактов — фронт узнаёт об изменении контракта событием, а не падением.

## 16. Сквозные подсистемы

|Подсистема|Решение|
|---|---|
|**Tenancy**|изоляция тенантов схемами БД; та же граница для кэша, файлов, jobs, FSM и интеграций; системные операции — в отдельном control-scope|
|**Realtime**|SSE-события поверх реестра: смена контракта, инвалидации — клиент подписывается, а не поллит|
|**Наблюдаемость**|ядро эмитит нейтральные события по декларативной политике; экспортёры (Prometheus / OpenTelemetry) — отдельные пакеты, их SDK в ядре забанен|
|**Секреты**|шифрование чувствительных полей конфигурации, генерация ключей CLI|

# Часть IV. Расширения и экосистема

## 17. Расширение — единица поставки

Расширение — иммутабельная декларация вкладов. Полный набор слотов: ресурсы, admin-страницы, кастомные методы, произвольные роутеры, фабрики ресурсных роутеров, роли, метаданные БД, сидеры, интеграции (connections / actions / triggers), jobs, runtime-определения для внешних исполнителей, standalone-контракты, провайдеры аутентификации.

Сборщик сливает вклады всех расширений в один бандл и **жёстко проверяет уникальность** каждого пространства имён — ресурсы, таблицы, методы, маршруты, роли, jobs; коллизия двух расширений ловится на старте с указанием виновных. Ядро само оформлено как расширение с теми же слотами (системные ресурсы, ретеншн-job, базовые роли): один контракт для всех, у ядра нет привилегированного API.

## 18. Опциональное — в опциональных пакетах

Правило зрелости: ядро не растёт «внутрь», возможности растут «вширь» пакетами. Держится машинно, а не договорённостью:

- **линтер банит импорты**: HTTP-клиенты — только внутри интеграционной границы; SDK метрик — только в пакетах-экспортёрах; async-ORM — нигде;
- **расширение должно зарабатывать место**: пакет с нулевыми потребителями удаляется; его полезная часть, если повторяется, въезжает в ядро маленьким примитивом (так умер отдельный аналитический пакет — а агрегатное чтение стало ядровым, §10);
- кастомный паттерн, повторённый 2–3 раза в проектах, — кандидат в пакет или ядро.

## 19. Карта экосистемы

Реальная экосистема вокруг ядра — ~20 пакетов; карта того, что вообще бывает расширением:

|Группа|Примеры|Механизм встраивания|
|---|---|---|
|**Инфраструктурные адаптеры**|кэш (Redis), очереди (Kafka), почта, файлообмен (SFTP), пуш-уведомления|коннекторы workflow + бэкенды политик ядра|
|**Наблюдаемость**|мосты в Prometheus / OpenTelemetry|sink на события ядра; SDK живёт только здесь|
|**Модель данных**|гео-поля (PostGIS), векторные поля + endpoint поиска|DSL полей; ядро включает поддержку при наличии поля|
|**Домены**|биллинг, продуктовая аналитика событий|полные bounded contexts: ресурсы + методы + jobs + роли|
|**Аутентификация**|OIDC, пароль, SMS, соцсети|слот auth-провайдеров; механика сессий — в ядре|
|**Клиенты**|кодоген TS / Dart + тонкие SDK-рантаймы|§20|
|**ИИ-грань**|LLM-адаптеры, MCP-доступ|§21|
|**Admin**|backend-driven оболочка, рендерер форм по JSON Schema|frontend-расширения, ведомые манифестом|
|**Миграционная оснастка**|parity-инструмент для переписывания legacy|offline-CLI, не рантайм (§26)|

## 20. Кодоген клиентов: один дескриптор — все поверхности

Самая показательная цепочка single source of truth:

```
Resource / CustomMethod (реестр)
   → клиентский контракт: JSON-манифест — схемы read/create/update из тех же
     моделей валидации, FSM-мета, права, запросные поля, contract_hash
   → языковой генератор (TS / Dart): DTO, схемы для форм,
     типизированные фасады операций, хелперы FSM-переходов
   → тонкий SDK-рантайм: CRUDL-семантика, идемпотентность,
     кэш с ETag и тег-инвалидацией, SSE
```

Свойства, ради которых это работает:

- контракт экспортируется **из тех же расширений, что собирают сервер**, — рассинхрон невозможен по построению;
- `contract_hash` связывает клиент и сервер: клиент детектирует смену контракта;
- генерация детерминирована (стабильная сортировка, стабильные хэши) → сгенерированное коммитится и ревьюится диффом;
- поверхности (`client / admin / integration / internal`) нарезают из одного реестра разные API; права в контракте — метаданные для UI, enforcement остаётся на сервере.

Одно объявление ресурса порождает сервер, админку, OpenAPI и типизированные клиенты для веба и мобильного. Это кодовый аналог правила БА «факт живёт в одном месте».

## 21. ИИ-грань: фреймворк и модели

Две разные грани:

- **LLM-адаптеры** — то, чем пользуется *приложение*: провайдеры моделей со structured output, durable-экшены для батчей (с ограничением конкурентности), реестр промптов как обычные ресурсы — с FSM жизненного цикла кэша, аудитом и правами. Работа с LLM встроена в те же контракты, что остальной домен, а не живёт сбоку скриптами.
- **MCP-доступ** — то, через что *внешний агент* работает с системой: MCP-эндпоинт с инструментами точечного редактирования (обзор → поиск → патч одного блока → публикация), под актором с правами и профилем доступа, сужающим видимость до ресурсов/зон/полей. Ключевое: MCP **не обходит** бизнес-правила — каждая запись идёт через обычный CRUDL с валидацией, row-scope, аудитом, идемпотентностью и FSM. Агент рассуждает о продукте, а не переписывает страницы целиком.

# Часть V. Само-верификация

## 22. Валидация реестра на старте

Первая линия — приложение не поднимется с противоречивой декларацией. На старте прогоняется пакет валидаторов (в реальном ядре их ~24): права методов существуют, роли не конфликтуют, `invalidates` ссылаются на живые ресурсы, FSM-переходы достижимы, контракты согласованы. Ошибка конфигурации — это ошибка запуска, а не сюрприз в проде.

## 23. Два снимка: хранение и контракт

Дрифт ловится сравнением детерминированных снимков, и их **два разных**:

|Снимок|Фиксирует|Хэш меняют|
|---|---|---|
|**storage** — форма БД|таблицы, колонки, типы, nullable, default'ы, индексы, FK|только изменения хранения|
|**contract** — публичный API|поля, операции, схемы, права, FSM-мета|только изменения контракта|

Разделение принципиально: семантика единицы поля меняет смысл — и не двигает ни один хэш; переименование admin-колонки меняет contract, но не storage. Каждый снимок — стабильный JSON → sha256; версия схемы реестра — отдельное целое число.

## 24. Дрифт-план и миграции

Сравнение снимков возвращает изменения с severity:

|Severity|Примеры|
|---|---|
|`danger`|удалён ресурс/колонка; NOT NULL без default (нужен backfill); смена типа (нужен cast); смена FK; смена имени таблицы (ревьюить как rename, не drop/create)|
|`warning`|смена default; новый индекс; удалён check|
|`info`|добавлен ресурс; поле стало nullable|

Снимок хранения пишется **под каждую ревизию миграций** — план дрифта считается против зафиксированной точки, а не «против вчера»; сами миграции и снимки принадлежат проекту, фреймворк даёт машинерию. Цикл изменения: правка декларации → план (severity) → черновик миграции → ревью → тесты. API версионируется отдельно от БД: ломающее изменение публичной операции — новый код (`*.v2`); миграция БД никогда не создаёт версию API автоматически.

## 25. Архитектурный линтер

Главный guardrail agent-first фреймворка. Типы и компилятор проверяют форму; линтер проверяет **архитектуру** — в реальном ядре полсотни правил про то, что типами не выражается:

|Категория|Примеры находок|
|---|---|
|Слои|бизнес-логика в роутере; сервис дёргает свой REST; транспортные детали в handler'е|
|Границы|HTTP-клиент вне интеграционной границы; транзакция поверх внешнего вызова; sleep-ретраи вместо workflow|
|Framework-owned|ручной аудит/кэш/CRUD там, где есть политика; UPDATE-перепись статуса мимо FSM; литеральная строка права вместо декларации; агрегат руками в сервисе|
|Качество данных|N+1 в цикле; сырой SQL; наивные datetime без таймзоны|
|Гигиена|файл превышает бюджет строк → команда разрезателя (§29); версия не поднята при ломающем изменении|

Режимы: **observe** (сигналы) → **guide** (smell = warning) → **enforce** (нарушение = error, перед сдачей). Baseline-файл делает линтер применимым на живом коде — падает только на новом (тот же храповик, что в [аудите графа](02_Граф.md)). У каждого правила — `explain` с плохим/хорошим примером и способом подавления; вывод в SARIF для CI. В среде агента линтер висит **хуком после каждой правки файла** — нарушение возвращается модели немедленно, а не на ревью.

## 26. Тесты фреймворка

- **Контрактные**: снимок → опасное изменение → проверка, что план пометил его `danger`; стабильность хэшей и версии схемы.
- **Фикстуры линтера**: пары `bad_* / ok_*` файлов на каждое правило — правило задокументировано исполняемым примером.
- **Parity для legacy**: при переписывании старой системы — декларативная карта соответствия (какое legacy-поле куда легло: перенесено / свёрнуто в JSON / покрыто примитивом рантайма / намеренно опущено) + детерминированная сверка данных и структурное покрытие. Миграция **доказывается** отчётом, а не «выглядит похоже». Аналогичный parity-подход — для wire-контрактов очередей, без живого брокера.
- Маркер «без БД» отделяет чистые registry-тесты от интеграционных — быстрый контур для агента.

# Часть VI. Агентная обвязка

## 27. Операционный контракт и скиллы

`AGENTS.md` — единый контракт репозитория; `CLAUDE.md` — симлинк на него: один текст для всех агентских сред, нет дрейфа между ассистентами. Содержание: что framework-owned, лестница путей данных (§2), классификация интеграций, правила синхронного ядра, команды качества.

В проект-потребитель обвязка ставится командой инициализации — фреймворк приносит свои процедуры с собой (как граф-инструмент приносит свои скиллы). Типовой набор: стиль, архитектура, «создай ресурс реестра», «создай кастомный метод», админка, интеграция, quality gates, parity очередей, миграция legacy-данных. Плюс хуки линтера на правку файлов и пре-коммит.

## 28. Карта проекта для агента

CLI-навигация уровнями зума, чтобы агент не читал репозиторий:

|Команда|Отвечает|
|---|---|
|`context atlas`|обзор: домены, сервисы, jobs, границы|
|`context area <цель>`|окрестность одной области|
|`context flow <вход>`|трасса: endpoint → сервисы → рантайм → инвалидации → интеграции|
|`context object <символ> --zoom calls\|impact`|контракт объекта, дерево вызовов, кто зависит|
|`registry-context …`|машинные срезы реестра: методы, маршруты, интеграции, ландшафт (JSON)|

Это кодовый аналог `node`/`impact` графа: агент спрашивает структуру, а не восстанавливает её чтением. Остальной CLI закрывает жизненный цикл: проверка/снимок/план реестра, миграции, сиды, тенанты, jobs, инвалидация кэша, скаффолд нового проекта.

## 29. Разрезатель исходников

Отдельный инструмент: AST-безопасное разбиение разросшегося файла на модули — побайтовый перенос тел символов, хирургия импортов, проверка циклов и бюджета строк. Работает по JSON-плану: инструмент предлагает безопасные группы переноса и помечает символы, которые двигать нельзя; агент решает, как группировать по ответственности и как назвать модули. Разделение труда: механика у инструмента, семантика у агента. Линтер находит файл-переросток и сам печатает готовую команду; ревью — обычный diff с подсветкой перемещений.

## 30. Замыкание на граф

Декларации несут **трассировку к артефактам**: ресурс и кастомный метод объявляют, какие правила/AC они реализуют (`implements`). Вторым каналом работает **observed-экспорт**: декларации (ресурсы, методы, jobs, интеграции) выгружаются в [граф](02_Граф.md) как узлы реализации — факт «ресурс существует» попадает в граф из кода, а не со слов. Кодовая семья перестаёт быть отдельным миром: `impact` от решения на встрече доходит до конкретного ресурса, а `gate` изменения видит, что контрактный артефакт реализован.

# Часть VII. Собрать свой

## Рецепт

1. **Найди boilerplate.** Что ИИ переписывает в каждой фиче (CRUD, валидация, права, проводка)? Это забирает фреймворк.
2. **Спроектируй дескриптор** (Resource / Field): минимальный набор, полностью задающий механику. Дескриптор — язык-нейтральный контракт; рантайм сменяем, шов для внешних исполнителей закладывается декларациями.
3. **Построй генераторы**: поле → колонка; ресурс → модели + роутер. Начни с in-memory CRUD над 2–3 ресурсами.
4. **Сделай рантайм-движок** с политиками из деклараций; API для сервисов — публичный и скучный.
5. **Определи escape hatch**: лестница CRUD → метод → сырой роут; слои; запрет схлопывания бизнес-логики в генерёжку.
6. **Добавь снимки и дрифт-план** (storage + contract, severity, привязка к миграциям) и валидацию деклараций на старте.
7. **Напиши архитектурный линтер** — хотя бы 5–10 правил про свои границы, с baseline, explain-примерами и хуком в среде агента. Без него правила живут в голове.
8. **Оформи механизм расширений** (слоты + проверка уникальности на сборке) — даже если расширение пока одно: это заставит ядро иметь публичные контракты.
9. **Собери агентную обвязку**: операционный контракт, скиллы типовых задач, CLI-карту.
10. **Замкни на граф**: `implements`-трассировка и observed-экспорт деклараций.
11. **Итерируй**: паттерн, повторённый 2–3 раза, — кандидат в ядро; расширение без потребителей — на удаление.

Порядок важен: дескриптор и генераторы дают ценность в первую неделю; линтер и обвязка превращают фреймворк из библиотеки в рельсы для агента; кодоген клиентов и платформенные подсистемы наращиваются по мере боли.

## На стадиях проекта

|Стадия|Что делает код-фреймворк|
|---|---|
|**Greenfield**|декларации первыми → скелет генерится → ИИ пишет бизнес-логику|
|**Brownfield**|реестр поверх существующих таблиц; дрифт против живой БД; parity-карта при переписывании|
|**Изменение**|правка декларации → план (severity) → миграция → ревью → контракт-тесты|
|**Масштаб / команда**|машиночитаемые декларации + линтер с хуками → много агентов без коллизий|
|**Передача / долгожитие**|контракт (декларации + операционный контракт) долговечен; сгенерированное одноразово; стек обычный — без lock-in|

## Definition of done

- [ ] Декларация — единственный источник контракта (история БД — миграции).
- [ ] Сгенерированное не правится руками; бизнес-кода там нет.
- [ ] Слои разделены; лестница путей данных соблюдается; интеграции классифицированы.
- [ ] Противоречивая декларация не даёт приложению стартовать.
- [ ] Снимки storage/contract и дрифт-план стоят в CI.
- [ ] Архитектурный линтер с baseline и explain стоит хуком у агента.
- [ ] Операционный контракт един для всех агентских сред.
- [ ] Клиентские поверхности генерятся из реестра, не пишутся руками.
- [ ] Декларации трассируются к артефактам (`implements` + observed-экспорт) — код виден графу.

Место в цикле → [ИИ-кодинг](../02_Процесс/04_ИИ_кодинг.md). Семья и сравнение → [Что такое фреймворк и граф](../01_Концепция/02_Фреймворк_и_граф.md).
