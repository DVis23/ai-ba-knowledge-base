# Код-фреймворк

Документные фреймворки (БА, спеки, архитектура) переиспользуешь как есть — markdown + ID + граф домен-агностичны. **Код-фреймворк привязан к стеку**: связка веб-фреймворк + ORM + слой данных у каждого своя. Готовый под твой стек редко подходит, поэтому собрать его — замыкающая компетенция фулл-стек ИИ-специалиста.

Принцип тот же, что у [БА-фреймворка](03_БА_фреймворк.md): **зафиксируй форму, освободи содержание, проверь автоматически**. Разница в материале — форма исполняемая (декларации + кодогенерация), проверка — типы и тесты, не граф. Ниже — архитектура, достаточная, чтобы спроектировать свой.

## Принцип: декларация → генерация → рантайм

Один водораздел определяет всё: **«сохрани строку» против «сделай что-то»**.

|Зона|Кто пишет|
|---|---|
|Механика — «сохрани строку»|фреймворк **генерит** из декларации|
|Бизнес-логика — «сделай что-то»|ИИ пишет руками в узкой зоне|

Цикл: объявил ресурс декларативно → фреймворк сгенерил таблицу, модели, эндпоинты, OpenAPI → рантайм исполняет CRUD с политиками. Boilerplate, который ИИ переписывал бы каждый раз, рождается детерминированно.

## Из чего собран

```
Declaration (Resource + Field)
        │  генераторы
        ├──▶ таблица БД (через ORM)
        ├──▶ модели валидации (create/update/read, OpenAPI)
        ├──▶ HTTP-роутер (CRUD-эндпоинты)
        └──▶ admin-метаданные / типы фронта / черновик миграции
        │
        ▼  рантайм-движок
   CRUD + политики (RBAC, row-scope, cache, audit, idempotency, FSM)
        │
   escape hatch ──▶ services («сделай что-то») + кастомные роутеры
        │
   bundle ──▶ собирает ресурсы/роутеры/jobs из многих расширений
        │
   drift-checks ──▶ snapshot + compare (само-верификация)
```

### 1. Декларация: `Resource` + `Field`

Сердце фреймворка. Ресурс описывается **данными**, не кодом:

```python
@dataclass(frozen=True)
class Field:
    code: str                 # имя поля
    type: str                 # int | string | datetime | json | …
    required: bool = False
    readonly: bool = False
    list: bool = False        # видимо в списке
    filter: bool = False      # доступна фильтрация
    unique: bool = False
    default: Any = None

@dataclass(frozen=True)
class Resource:
    name: str
    table_name: str
    fields: tuple[Field, ...]
    permissions: dict[str, str]            # {"read": "...", "write": "..."}
    relations: tuple[Relation, ...] = ()
    indexes: tuple[Index, ...] = ()
    cache: CachePolicy | None = None
    audit: AuditPolicy | None = None
    state_machine: StateMachinePolicy | None = None
    # …и другие политики
```

```python
group = Resource(
    name="groups", table_name="groups",
    fields=(Field("id", "int", readonly=True),
            Field("name", "string", required=True),
            Field("is_active", "bool", default=True)),
    permissions={"read": "groups.read", "write": "groups.write"},
)
```

Декларация — единственный источник правды о контракте ресурса. Историю БД держат миграции, не она.

### 2. Генераторы: декларация → артефакты

|Из чего|Во что|
|---|---|
|`Field`|колонка ORM + constraints + indexes → таблица|
|`Resource`|модели валидации `create/update/read`|
|`Resource`|HTTP-роутер|
|`Resource`|admin-метаданные, OpenAPI, типы фронта, черновик миграции|

Сгенерированный роутер по декларации монтирует:

```
GET    /<name>          list (фильтры, сортировка, пагинация)
GET    /<name>/{id}
POST   /<name>
PATCH  /<name>/{id}
DELETE /<name>/{id}
GET    /<name>:meta      метаданные для admin
POST   /<name>/{id}:transition   (если есть state_machine)
```

**Сгенерированное руками не правят** — бизнес-код туда не попадает.

### 3. Рантайм-движок: CRUD с политиками

Один движок (`list/create/update/delete`) исполняет все ресурсы, применяя политики из декларации: фильтры/сортировка/пагинация, RBAC и row-scope, cache, audit, idempotency, FSM-переходы. Добавил политику в `Resource` — поведение появилось без нового кода эндпоинта.

### 4. Escape hatch: куда уходит бизнес-логика

Что CRUD не выражает (чекаут, вебхук, расчёт) — пишется явно: пометить действие как «реализовано расширением» + подключить свою функцию; кастомные роутеры для нетиповых эндпоинтов; сервисы для доменной логики. Слои с жёсткими ролями:

|Слой|Отвечает|Не делает|
|---|---|---|
|Роутер|HTTP: парсинг, auth, маппинг DTO|бизнес-решений|
|Сервис|инварианты, расчёты, мультизапись, FSM|транспорт|
|Рантайм-API|таблицы реестра, idempotency, audit|—|
|Адаптер|SDK провайдера, HTTP, очередь|бизнес-решений|

Правило: реестр — «сохрани строку», сервисы — «сделай что-то». Не схлопывать бизнес-логику в роутер или в генерёжку.

### 5. Bundle: сборка из расширений

Расширение — единица поставки: несёт `resources`, `routers`, `jobs`, `integrations`, `seeders`, роли. Сборщик собирает из многих расширений один рантайм, проверяя дубликаты. Границы: расширение зависит от публичных контрактов ядра, не от чужих внутренностей. Опциональное — отдельными пакетами, включается выбором.

### 6. Drift-checks: само-верификация

Линтер кодовой семьи. Снимок схемы даёт стабильный хэш; сравнение снимков возвращает изменения с уровнем (`danger` — удалён ресурс/поле, `info` — добавлен):

```
check    валидна ли декларация
snapshot сохранить снимок схемы
plan     diff снимков (drift)
drift    декларация ≠ реальная БД
```

Проверяет, что декларация ↔ БД ↔ OpenAPI ↔ admin не разошлись. Правило без автопроверки живёт только в голове автора.

### Декларативны и остальные абстракции

FSM (states, initial, transitions с permission/set_fields), jobs (handler, schedule, batch), интеграции (connection/action/trigger с retry/timeout) — тоже объявляются данными, не размазываются по коду.

## Почему укрощает ИИ

|Проблема LLM|Чем снимает код-фреймворк|
|---|---|
|Стохастичность|boilerplate генерится детерминированно; ИИ не пишет то, что плывёт от прогона к прогону|
|Контекст|ИИ читает машиночитаемые декларации, не репозиторий — узкие пакеты задач|
|Невалидируемость|типы + drift-checks + контракт-тесты делают вывод проверяемым; компилятор = линтер|

«AI-native» — *код удобно инспектировать и проверять*, а не «логика спрятана за DSL». Утопил смысл в декларациях — сломал фреймворк.

## Рецепт сборки

1. **Найди boilerplate.** Что ИИ переписывает в каждой фиче (CRUD, сериализация, валидация, проводка)? Это забирает фреймворк.
2. **Спроектируй дескриптор** (`Resource`/`Field`). Минимальный набор, полностью задающий механику.
3. **Построй генераторы.** Поле → колонка, ресурс → модели + роутер. Начни с in-memory CRUD над 2–3 ресурсами, потом реальное хранилище.
4. **Сделай рантайм-движок** с политиками (RBAC, cache, audit) из декларации.
5. **Определи escape hatch и слои.** Запрети схлопывание бизнес-логики в генерёжку.
6. **Добавь drift-checks** (snapshot + compare) и контракт-тесты.
7. **Напиши `AGENTS.md`** — операционный контракт для ИИ: команды, когда уходить в кастом, границы пакетов.
8. **Итерируй.** Кастомный паттерн, повторённый 2–3 раза, — кандидат в ядро.

> Дескриптор переносим: один и тот же контракт `Resource/Field` можно реализовать на разных языках/рантаймах (например Python и Go). Декларация и генерация разные, контракт один — ценность в дескрипторе, рантайм сменяем.

## На всех стадиях проекта

|Стадия|Что делает код-фреймворк|
|---|---|
|**Greenfield**|декларации первыми → движок генерит скелет → ИИ пишет бизнес-логику|
|**Brownfield**|реестр поверх существующих таблиц; `drift` против живой БД; миграция инкрементально|
|**Изменение**|правка декларации → `plan` → черновик миграции → ревью → regenerate → контракт-тесты|
|**Масштаб / команда**|машиночитаемые декларации + явное владение → много агентов без коллизий|
|**Передача / долгожитие**|контракт (декларации + `AGENTS.md`) долговечен; сгенерированный код одноразов|

## Definition of done

- [ ] Декларация — единственный источник контракта (история БД — миграции).
- [ ] Сгенерированное не правится руками; бизнес-кода там нет.
- [ ] Слои разделены: бизнес-логика не в роутере и не в генерёжке.
- [ ] Drift-checks и контракт-тесты проходят, стоят в CI.
- [ ] `AGENTS.md` есть: команды, границы, классификация интеграций.
- [ ] ИИ пишет только «сделай что-то»; «сохрани строку» закрыто фреймворком.
