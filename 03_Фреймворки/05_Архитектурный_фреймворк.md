# Архитектурный фреймворк

Документная семья для разработки: фиксирует **архитектуру и поведение** приложения в управляющих артефактах. Тот же движок [триады](01_Триада.md), что у БА, но домен — не бизнес, а как система устроена и ведёт себя. Ниже — паттерн на примере фреймворка архитектурной документации (характерно для мобильных и фронтенд-приложений, переносится шире).

Идея: приложения страдают не от сложности кода, а от размытых границ и неформализованного поведения UI. ИИ это усиливает — без явных контрактов он догадывается. Фреймворк превращает документы в **ограничители сложности**: каждый аспект — в отдельном связанном артефакте.

## Артефакты

|Артефакт|Фиксирует|Слой|
|---|---|---|
|Architecture Overview (C4)|границы системы, внешние интеграции, нефункц. требования|архитектура|
|Module Boundaries|слои `ui → presentation → domain → data`, правила зависимостей|архитектура|
|ADR|ключевое тех-решение: контекст / решение / последствия|архитектура|
|Feature Spec|цель, сценарии, экраны, use cases, домен, кеш, деградация|поведение|
|Screen State Machine|состояния, действия, эффекты, таблица переходов|поведение|
|**Behavior Slice**|вертикальный срез поведения для реализации|реализация|
|API Contracts / Error Model|операции, маппинг DTO↔Domain, единая модель ошибок|контракт|

## Behavior Slice — единица работы для ИИ

Центральный артефакт. Минимальный вертикальный срез через все слои с наблюдаемым результатом. Поля:

|Поле|Назначение|
|---|---|
|`id`, `priority`|ID + приоритет `P0/P1/P2`|
|`context.preconditions`|предусловия|
|`trigger`|событие-инициатор|
|`expectedBehavior`|наблюдаемое поведение|
|`stateCoverage`|какие состояния State Machine покрыты|
|`acceptanceCriteria`|`given / when / then` — приёмка|
|`implementationHints`|**подсказки ИИ для генерации кода**|

`implementationHints` — то, что делает срез готовым к ИИ-кодингу. Он несёт не поведение, а карту реализации:

- **fileStructure** — точные пути: `domain/usecases/<…>`, `data/`, `presentation/`, `ui/`;
- **classFunctionNames** — имена: `LoadContentUseCase`, `ContentRepository`, `ContentViewModel`;
- **dependencies** — core-модули, другие фичи, внешние либы;
- **testStructure** — пути тестов по слоям.

ИИ получает срез — и пишет код в заданную структуру, не выдумывая, куда что класть. Это документный аналог того, как код-фреймворк убирает boilerplate.

## Трассировка и валидация

Связи по ID (`FEATURE-`/`SCREEN-`/`SLICE-`) + центральный реестр артефактов. Проверяет скрипт валидации:

- **обязательные секции** по типу артефакта;
- **формат ID** (regex) и наличие блока `Artifact ID`;
- **трассировку**: `Feature ID` обязателен в Slice и State Machine; `Screen ID` в State Machine = Artifact ID;
- **валидность ссылок**: ID существует в реестре.

Плюс JSON-схемы (Feature Spec, Behavior Slice, State Machine) валидируют форму документа. Запуск в CI — стандартный quality gate.

## Дорожная карта: когда какой артефакт

6 этапов с acceptance-критериями:

|Этап|Артефакты|Частота|
|---|---|---|
|1. Архитектурные рамки|Overview, Module Boundaries, 2–3 ADR|один раз на проект|
|2. Проектирование фичи|Feature Spec, State Machine|на каждую фичу|
|3. Контракты|API Contracts, Error Model, golden samples|на фичу|
|4. Behavior Slices|нарезка фичи на срезы|на фичу|
|5. Тестирование|Test Strategy, Quality Gates|один раз + развитие|
|6. Навигация / Observability / Release|routes, logging, релиз|по мере роста|
