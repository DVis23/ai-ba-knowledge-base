# Plan mode

Режим, в котором Claude проектирует план, не выполняя изменений. Выход — через явное подтверждение пользователя (`ExitPlanMode`).

## Зачем существует

1. **Дорогие/необратимые действия требуют ревью.** Миграция БД, рефакторинг 30 файлов, новое API — сначала план, потом действие.
2. **Незнакомая область — высокая стохастика.** План вытаскивает наружу скрытые предположения модели.
3. **Чек-лист до старта.** Видишь шаги — убираешь out-of-scope, добавляешь пропущенное, правишь порядок.

## Когда план, когда сразу

- Задача затрагивает > 2 файлов или незнакомую область → план.
- Одна точечная правка с понятным контрактом → сразу.
- Пользователь явно просит «сначала покажи план» → план, без интерпретации.
- Цена ошибки высока (миграция, релиз, продакшн) → план даже на маленькую правку.

## Что в плане

- Список шагов с **файлами и характером правки** (Edit / Write / Bash / tool).
- **Тред-оффы**, если их > 1. Если выбор очевиден — не пиши «варианты есть».
- **Чего НЕ делаем** — явный out-of-scope. Без этого scope расползается на исполнении.

## Что НЕ в плане

- Tutorial-объяснения зачем нужен Edit или как работает git.
- Код целиком — только сигнатуры/диффы крупными мазками.
- «Сначала разберусь, потом расскажу» — это не план, это TODO для себя.

## Plan mode ≠ Plan-агент

|Что|Когда|
|---|---|
|**Plan mode** (режим сессии)|Основной агент проектирует, не действует|
|**Plan-агент** (`subagent_type: Plan`)|Делегируешь проектирование в изолированный контекст, см. [../01_Основные/05_Agents.md](../01_Основные/05_Agents.md)|

Первое — режим; второе — инструмент делегирования.

## Связь с другими механизмами

- Skill может иметь собственный «шаг планирования» — см. [Skills.md](../01_Основные/04_Skills.md). Plan mode не нужен внутри skill, который уже структурирован.
- Hook может включать Plan mode на определённых условиях — см. [Hooks.md](02_Hooks.md).
